# 가상 메모리와 파일 시스템

## 1. 페이징을 통한 가상 메모리 관리

**가상 메모리(Virtual Memory)**는 프로세스에 독립적인 주소 공간을 제공하고, 실행에 필요한 부분만 물리 메모리에 적재해 **물리 메모리보다 큰 프로세스도 실행할 수 있게 하는 기술**이다.

- 대표적인 메모리 관리 기법으로 **페이징**과 **세그멘테이션**이 있으며, 여기서는 페이징을 중심으로 정리한다.
- 프로세스 전체를 한 번에 적재하지 않고, 필요한 부분을 메모리와 보조기억장치 사이에서 옮겨 사용한다.

### 1.1 페이지와 프레임

**페이징(Paging)**은 프로세스의 논리 주소 공간을 일정한 크기의 **페이지**로 나누고, 물리 메모리의 같은 크기 단위인 **프레임**에 불연속적으로 배치하는 방식이다.

| 용어 | 의미 |
| --- | --- |
| 페이지(Page) | 프로세스의 논리 주소 공간을 나누는 단위 |
| 프레임(Frame) | 페이지를 적재하는 물리 메모리의 단위 |
| 페이지 아웃(Page Out) | 페이지를 메모리에서 보조기억장치로 내보내는 것 |
| 페이지 인(Page In) | 필요한 페이지를 보조기억장치에서 메모리로 가져오는 것 |

- 프로세스를 연속된 물리 공간에 배치할 필요가 없어 **외부 단편화를 해결**한다.
- 마지막 페이지를 모두 사용하지 못하는 등, 할당된 공간 안에 빈 공간이 남는 **내부 단편화**가 발생할 수 있다.
- 페이지 크기를 줄이면 내부 단편화를 줄일 수 있지만, 관리할 페이지 수와 페이지 테이블 크기가 증가한다.
- **대형 페이지(Huge Page)**는 페이지 테이블과 TLB의 관리 부담을 줄이기 위한 방법이다. 내부 단편화를 해결하는 방법은 아니며, 사용하지 않는 공간이 더 커질 수 있다. [참고: Linux 메모리 관리 개념](https://kernel.org/doc/html/v5.19/admin-guide/mm/concepts.html#huge-pages)

## 2. 페이지 테이블과 주소 변환

**페이지 테이블(Page Table)**은 **페이지 번호와 프레임 번호의 대응 관계**를 관리한다. 물리 메모리에 흩어진 페이지를 프로세스의 논리 주소 공간에서는 연속된 공간처럼 사용할 수 있게 한다.

### 2.1 주소 변환 과정

논리 주소는 **페이지 번호와 변위(Offset)**로 구성된다.

1. 논리 주소에서 **페이지 번호**를 확인한다.
2. 페이지 테이블에서 대응하는 **프레임 번호**를 찾는다.
3. 프레임 번호와 기존 변위를 결합해 **물리 주소**를 얻는다.

- 페이지와 프레임의 크기가 같으므로 **변위는 변하지 않는다**.
- 물리 주소는 `프레임 번호 × 페이지 크기 + 변위`로 계산할 수 있다.

### 2.2 페이지 테이블 베이스 레지스터와 TLB

- 프로세스마다 자신의 주소 공간에 대한 페이지 테이블을 관리한다.
- **PTBR(Page Table Base Register)**은 현재 사용하는 페이지 테이블의 시작 주소를 가리킨다.
- 페이지 테이블의 위치 등 관리 정보는 **PCB**에 기록되며, 문맥 교환 시 새 프로세스에 맞게 관련 레지스터가 변경된다.

페이지 테이블이 메모리에 있으면, **단일 단계 페이지 테이블과 캐시가 없는 단순한 경우**에는 페이지 테이블 조회와 실제 데이터 접근에 각각 메모리 접근이 필요하다.

이를 줄이기 위해 CPU의 주소 변환 장치는 **TLB(Translation Lookaside Buffer)**에 최근 사용한 주소 변환 정보를 캐시한다.

| 구분 | 동작 |
| --- | --- |
| TLB 히트 | TLB에서 변환 정보를 찾아 페이지 테이블 조회를 줄임 |
| TLB 미스 | 페이지 테이블을 조회해 변환 정보를 확인해야 함 |

- **TLB 미스가 곧 페이지 폴트를 의미하지는 않는다.** TLB에 정보가 없어도 해당 페이지가 메모리에 있을 수 있다.

### 2.3 페이지 테이블 엔트리(PTE)

페이지 테이블의 각 항목을 **페이지 테이블 엔트리(Page Table Entry)**라고 한다. 페이지 번호를 인덱스로 삼아 다음 정보를 확인한다.

| 정보 | 의미 |
| --- | --- |
| 프레임 번호 | 페이지가 적재된 물리 프레임의 번호 |
| 유효 비트 | 여기서는 메모리 상주 여부를 나타내는 비트로 설명. 적재되어 있으면 1, 없으면 0 |
| 보호 비트 | 읽기·쓰기·실행 등의 접근 권한을 표시 |
| 참조 비트 | 최근 초기화 이후 페이지에 접근했는지 표시 |
| 수정 비트(Dirty Bit) | 보조기억장치의 내용과 동기화된 이후 페이지가 수정되었는지 표시 |

- 비트의 명칭과 구성은 CPU 구조에 따라 다르며, **주소의 유효성과 메모리 상주 여부를 구분**하기도 한다.
- 메모리에 없는 페이지에 접근하면 **페이지 폴트(Page Fault)**가 발생한다. 운영체제는 유효한 접근인지 확인한 뒤 필요한 페이지를 준비한다.
- 수정된 페이지를 교체할 때는 변경 내용을 보조기억장치에 반영해야 한다. 수정되지 않았고 보조기억장치에 동일한 사본이 있다면 다시 기록할 필요가 없다.

### 2.4 페이지 공유와 쓰기 시 복사

- 여러 프로세스의 페이지 테이블이 **같은 물리 프레임을 가리키면** 페이지를 공유할 수 있다. 공유 라이브러리의 코드 등이 대표적인 예다.
- **쓰기 시 복사(Copy-on-Write)**는 `fork()` 이후 부모와 자식이 페이지를 공유하다가, 어느 한쪽이 쓰기를 시도하면 **해당 페이지를 복사해 분리**하는 방식이다.

### 2.5 계층적 페이징

**계층적 페이징(Hierarchical Paging)** 또는 **다단계 페이지 테이블**은 페이지 테이블을 여러 단계로 나누어 관리하는 방식이다.

- 바깥쪽 페이지 테이블이 하위 페이지 테이블을 가리키고, 마지막 단계에서 실제 프레임을 찾는다.
- 사용하지 않는 주소 영역에 대한 하위 테이블을 만들지 않아 **페이지 테이블의 메모리 낭비를 줄일 수 있다**.
- 단계가 많아지면 주소 변환을 위한 조회도 늘어나므로 TLB가 중요하다.

## 3. 요구 페이징과 페이지 교체

### 3.1 요구 페이징(Demand Paging)

프로세스를 실행할 때 모든 페이지를 미리 적재하지 않고 **실제로 필요한 페이지부터 메모리에 적재**하는 기법이다.

- **순수 요구 페이징**은 프로세스의 페이지를 미리 적재하지 않고 실행을 시작해, 첫 접근부터 페이지 폴트를 통해 필요한 페이지를 가져온다.
- 안정적인 실행을 위해서는 **어떤 페이지를 교체할지**와 **프레임을 얼마나 배정할지**를 결정해야 한다.

페이지가 보조기억장치에 있는 경우의 기본 처리 흐름은 다음과 같다.

1. 페이지 폴트가 발생하면 운영체제가 접근의 유효성을 확인한다.
2. 빈 프레임을 확보하고, 없다면 교체할 페이지를 선택한다.
3. 필요한 경우 교체 대상의 수정 내용을 저장한 뒤 요청한 페이지를 적재한다.
4. 페이지 테이블 등 주소 변환 정보를 갱신하고 중단된 명령어를 다시 실행한다.

### 3.2 페이지 교체 알고리즘

**페이지 교체 알고리즘**은 메모리 공간을 확보하기 위해 내보낼 페이지를 선택하는 기준이다. 같은 **페이지 참조열과 프레임 수**에서 페이지 폴트 횟수를 비교해 평가할 수 있다.

| 알고리즘 | 교체 기준 | 특징 |
| --- | --- | --- |
| FIFO | 메모리에 가장 먼저 들어온 페이지 | 단순하지만 자주 쓰는 페이지도 교체할 수 있음 |
| 2차 기회(Second Chance) | FIFO 순서로 검사하되 참조 비트가 1이면 교체를 미룸 | 참조 비트를 0으로 바꾸고 다음 후보를 검사하며, 0인 페이지를 교체 |
| 최적(OPT) | 앞으로 가장 늦게 다시 사용할 페이지 또는 다시 사용하지 않을 페이지 | 미래의 참조 정보를 알아야 하므로 주로 비교 기준으로 활용 |
| LRU(Least Recently Used) | 과거에 가장 오랫동안 사용하지 않은 페이지 | 최근 사용 이력을 바탕으로 선택 |

- **최적 알고리즘의 기준은 미래의 다음 사용 시점**이다. 사용 빈도가 가장 낮은 페이지를 선택하는 방식과 구분해야 한다. [참고: OSTEP 페이지 교체 정책](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-beyondphys-policy.pdf)
- **2차 기회**는 페이지를 실제로 다시 적재하는 것이 아니라, 참조 비트를 확인해 교체 순서를 뒤로 미루는 방식이다.

## 4. 스래싱과 프레임 할당

**스래싱(Thrashing)**은 페이지 폴트가 지나치게 자주 발생해 **실제 실행보다 페이지를 옮기는 데 더 많은 시간을 쓰는 현상**이다.

- 좋지 않은 교체 정책뿐 아니라 **프로세스에 필요한 프레임이 부족한 경우**에도 발생한다.
- 메모리에 함께 적재되어 실행에 참여하는 프로세스 수를 **멀티프로그래밍의 정도**라고 한다.
- 프로세스 수를 지나치게 늘리면 각 프로세스가 확보하는 프레임이 줄어 **CPU 이용률이 오히려 낮아질 수 있다**.

### 4.1 프레임 할당 방식

| 구분 | 방식 | 기준 |
| --- | --- | --- |
| 정적 할당 | 균등 할당 | 프로세스마다 같은 수의 프레임을 배정 |
| 정적 할당 | 비례 할당 | 프로세스 크기에 비례해 프레임을 배정 |
| 동적 할당 | 작업 집합 모델 | 최근 일정 기간 참조한 페이지 집합을 유지할 수 있도록 배정 |
| 동적 할당 | 페이지 폴트 빈도(PFF) | 폴트 빈도가 상한보다 높으면 추가 배정하고, 하한보다 낮으면 회수 |

- **작업 집합(Working Set)**은 프로세스가 최근 일정 기간 동안 참조한 페이지들의 집합이다.
- 전체 작업 집합을 유지할 프레임이 부족하다면, 동시에 실행에 참여하는 프로세스 수를 줄이는 등의 조치가 필요하다.

## 5. 파일과 디렉터리

파일과 디렉터리는 운영체제의 **파일 시스템**이 관리한다.

### 5.1 파일과 메타데이터

**파일(File)**은 보조기억장치에 저장된 관련 정보의 집합이다. 파일의 내용 외에 파일을 관리하는 부가 정보를 **속성 또는 메타데이터(Metadata)**라고 한다.

- 대표적인 속성: **유형, 크기, 접근 권한, 생성·접근·수정 시각, 소유자, 저장 위치** 등.
- **확장자**는 파일 유형을 나타내는 관례적인 표기이며, 실제 유형을 항상 보장하지는 않는다.
- 파일 생성·삭제·열기·닫기·읽기·쓰기 등의 연산은 운영체제가 제공하는 **시스템 호출**을 통해 수행한다.

### 5.2 디렉터리와 경로

**디렉터리(Directory)**는 파일과 하위 디렉터리를 묶어 관리하는 구조이며, 폴더라고도 한다.

- 하나의 디렉터리만 사용하는 **1단계 디렉터리 구조**에서, 여러 계층을 갖는 **트리 구조**로 확장할 수 있다.
- 트리 구조의 최상위 디렉터리를 **루트 디렉터리**라고 한다.
- 디렉터리도 생성·삭제·열기·닫기·읽기 등의 연산 대상이다.

| 경로 | 시작 기준 | 예시 |
| --- | --- | --- |
| 절대 경로 | 루트 디렉터리 | `/home/minchul/note.txt` |
| 상대 경로 | 현재 작업 디렉터리 | 현재 위치가 `/home`이면 `minchul/note.txt` |

### 5.3 디렉터리 엔트리

디렉터리도 파일의 한 종류이며, 내부에는 파일이나 하위 디렉터리를 찾기 위한 **디렉터리 엔트리(Directory Entry)**가 저장된다.

- 엔트리는 이름과 해당 대상의 메타데이터·위치에 접근할 수 있는 정보를 연결한다.
- 저장 형식은 파일 시스템마다 다르며, 유닉스 계열에서는 대표적으로 **파일 이름과 i-node 번호**를 연결한다.
- `/home/minchul`을 찾을 때는 루트에서 `home`을 찾고, 그 디렉터리에서 다시 `minchul`을 찾는다.

## 6. 파일 시스템과 파일 할당

**파일 시스템(File System)**은 파일과 디렉터리를 보조기억장치에 저장하고 접근할 수 있도록 관리하는 운영체제의 구성 요소다. 한 컴퓨터에서 여러 파일 시스템을 사용할 수 있다.

### 6.1 파티셔닝과 포매팅

| 용어 | 의미 |
| --- | --- |
| 파티셔닝(Partitioning) | 저장장치를 여러 논리적 영역으로 나누는 작업 |
| 파티션(Partition) | 파티셔닝으로 나뉜 각각의 영역 |
| 논리적 포매팅(Formatting) | 파일 시스템의 관리 구조를 만들어 파일을 저장·관리할 준비를 하는 작업 |
| 저수준 포매팅 | 저장장치의 물리적 기록 구조를 준비하는 작업. 장치에 따라 제조 단계 등에서 수행 |

- 일반적으로 파일 시스템을 만드는 포맷 작업은 **논리적 포매팅**을 뜻한다.

### 6.2 파일 할당 방법

파일 시스템은 저장 공간을 **블록** 등의 할당 단위로 관리한다. 파일을 배치하는 대표적인 방식은 **연속 할당**과, 불연속 할당에 속하는 **연결 할당·색인 할당**이다.

| 방식 | 저장 구조 | 주요 관리 정보 | 장점·한계 |
| --- | --- | --- | --- |
| 연속 할당 | 파일의 블록을 연속 배치 | 시작 블록 주소, 길이 | 접근이 빠르지만 외부 단편화와 파일 확장 문제가 발생 |
| 연결 할당 | 각 블록이 다음 블록의 주소를 저장 | 시작 블록 주소 등 | 흩어진 공간을 활용하지만 임의 접근이 느리고 연결 정보 손상에 취약 |
| 색인 할당 | 색인 블록에 데이터 블록 주소를 모아 저장 | 색인 블록 주소 | 임의 접근이 쉽지만 색인 블록을 위한 추가 공간이 필요 |

## 7. FAT과 유닉스 파일 시스템

### 7.1 FAT 파일 시스템

**FAT(File Allocation Table)**은 각 클러스터의 다음 클러스터 정보를 **별도의 파일 할당 테이블에 모아 관리**하는 방식이다.

- 파일 데이터 블록 안에 다음 주소를 넣는 기본 연결 할당의 한계를 보완한다.
- FAT은 볼륨 앞부분의 관리 영역에 위치하며, 실행 중 메모리에 캐시하면 연결 정보를 더 빠르게 탐색할 수 있다.
- 임의 위치를 찾을 때 연결 사슬을 따라가는 과정은 여전히 필요하지만, 데이터 블록을 매번 읽는 부담을 줄일 수 있다.
- FAT에서는 여러 섹터를 묶은 **클러스터(Cluster)**를 파일 공간 할당 단위로 사용한다.

### 7.2 유닉스 파일 시스템과 i-node

유닉스 계열의 전통적인 파일 시스템은 **i-node에 파일의 속성과 데이터 블록을 찾기 위한 주소 정보**를 저장한다.

- 파일마다 i-node가 있으며, 각각 **i-node 번호**로 식별한다.
- 디렉터리 엔트리는 **이름과 i-node 번호**를 연결하고, i-node는 **파일 속성과 데이터 블록 위치 정보**를 담는다.
- i-node는 단순한 블록 주소 목록보다 많은 메타데이터를 담는 구조다.

학습에 사용하는 대표적인 **15개 주소 항목 구조**는 다음과 같다.

| 주소 항목 | 저장하는 정보 | 데이터에 도달하는 방식 |
| --- | --- | --- |
| 1~12번째 | 직접 블록 주소 | 데이터 블록을 바로 가리킴 |
| 13번째 | 단일 간접 블록 주소 | 데이터 블록 주소 목록을 한 단계 거침 |
| 14번째 | 이중 간접 블록 주소 | 단일 간접 블록들의 주소 목록을 거침 |
| 15번째 | 삼중 간접 블록 주소 | 이중 간접 블록들의 주소 목록을 거침 |

- 주소 항목이 15개라고 해서 **파일 크기가 데이터 블록 15개로 제한되는 것은 아니다**. 간접 블록을 통해 더 많은 데이터 블록을 가리킨다.
- i-node의 정확한 구성은 파일 시스템에 따라 다르며, 모든 유닉스 계열 파일 시스템이 이 구조를 그대로 사용하는 것은 아니다. [참고: OSTEP 파일 시스템 구현](https://pages.cs.wisc.edu/~remzi/OSTEP/file-implementation.pdf)
- 대표적인 파일 시스템으로 Windows의 **NTFS**, Linux의 **ext 계열** 등이 있다.

## 8. 저널링 파일 시스템

파일 시스템의 여러 정보를 변경하는 도중 시스템이 중단되면 **일부 변경만 저장되어 일관성이 깨질 수 있다**.

**저널링(Journaling)**은 변경 내용을 **로그에 먼저 기록**해, 시스템 크래시 후 복구를 빠르게 수행하는 기법이다.

1. 변경 내용을 저널 영역에 기록한다.
2. 로그의 기록 완료를 확정한 뒤 실제 파일 시스템 위치에 변경을 반영한다.
3. 반영이 끝나면 해당 로그 공간을 재사용할 수 있게 한다.

- 복구 시에는 저널을 확인해 완료된 기록을 재반영하는 등의 방식으로 일관성을 회복한다.
- 메타데이터만 기록하는 방식과 데이터까지 기록하는 방식 등이 있으며, **저널링이 모든 파일 내용의 보존을 보장하는 것은 아니다**. [참고: OSTEP 크래시 일관성과 저널링](https://pages.cs.wisc.edu/~remzi/OSTEP/file-journaling.pdf)

## 9. 핵심 요약

1. **페이징**은 페이지를 프레임에 분산 배치해 외부 단편화를 해결하지만, 내부 단편화가 발생할 수 있다.
2. **페이지 테이블**은 논리 주소를 물리 주소로 변환하고, **TLB**는 변환 정보를 캐시한다.
3. **요구 페이징**은 필요한 페이지만 적재하며, **페이지 교체와 프레임 할당**이 성능을 좌우한다.
4. **최적 페이지 교체는 미래의 사용 시점**, **LRU는 과거의 사용 이력**을 기준으로 한다.
5. **스래싱**을 줄이려면 각 프로세스의 작업 집합을 유지할 수 있는 프레임을 확보해야 한다.
6. **디렉터리 엔트리**는 이름을 파일 관리 정보에 연결하고, 파일 시스템은 블록의 저장 위치를 관리한다.
7. **FAT은 연결 정보를 테이블에**, **전통적인 유닉스 파일 시스템은 속성과 블록 주소를 i-node에** 모아 관리한다.
8. **저널링**은 변경 로그를 이용해 시스템 중단 후 파일 시스템의 일관성 회복을 돕는다.
