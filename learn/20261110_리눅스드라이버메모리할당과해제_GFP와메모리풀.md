# 리눅스 디바이스 드라이버의 메모리 할당과 해제, GFP 플래그와 메모리 풀

리눅스 디바이스 드라이버에서 호출 문맥과 주소 연속성에 따라 메모리 할당 API를 고르는 방법을 정리한다. 일반 커널 버퍼, 연속된 물리 페이지, DMA 버퍼의 조건을 구분하고, 메모리 풀로 메모리 부족에 대비하는 방법과 플랫폼에 맞춰 자료형과 장치 레지스터를 다루는 방법을 살펴본다.

학습일 **2026-11-10**

## 1. 커널 메모리와 할당 문맥

1. **사용자 공간과 커널 공간**. 사용자 프로그램은 가변 크기 버퍼나 리스트의 노드를 `malloc()`으로 할당하고 `free()`로 반환한다. 리눅스 드라이버는 커널 주소 공간에서 실행되므로 같은 목적에 커널 할당 API를 사용한다. MMU는 페이지 테이블을 바탕으로 가상 주소를 물리 주소로 변환한다. 가상 주소가 연속되어도 각 페이지가 다른 물리 위치에 매핑될 수 있다. [사용자 공간의 할당 API](https://man7.org/linux/man-pages/man3/malloc.3.html), [리눅스의 가상 메모리](https://docs.kernel.org/admin-guide/mm/concepts.html)
2. **페이지와 단편화**. `PAGE_SIZE`는 기본 페이지의 바이트 수이고 `PAGE_SHIFT`는 `PAGE_SIZE = 1UL << PAGE_SHIFT`를 만족한다. 기본 페이지 크기는 아키텍처와 커널 설정에 따라 달라진다. 페이지 할당기는 물리 메모리를 페이지 단위로 관리하고, `kmalloc()`은 작은 요청에 페이지를 더 작은 객체로 나누어 쓸 수 있다. 할당과 해제가 반복되면 총 여유 메모리가 충분해도 필요한 만큼 연속된 물리 페이지를 확보하기 어려울 수 있다. [메모리 컴팩션과 단편화](https://docs.kernel.org/admin-guide/mm/concepts.html#compaction), [커널 메모리 할당 가이드](https://docs.kernel.org/core-api/memory-allocation.html)
3. **메모리 회수와 페이지 폴트**. 사용자 공간에서는 `malloc()`이 성공한 뒤에도 실제 페이지가 첫 접근 시 마련될 수 있고, 요청 자체가 실패할 수도 있다. 사용자 페이지가 스왑에 있으면 `copy_from_user()`나 `copy_to_user()` 중 페이지 폴트 처리로 호출이 잠들 수 있다. 드라이버가 `kmalloc()`이나 `vmalloc()`으로 확보한 버퍼는 사용 중 RAM에 유지된다. 새 커널 버퍼를 확보할 때는 플래그에 따라 페이지 캐시를 회수하거나, 페이지를 옮겨 빈 영역을 모으는 컴팩션을 시도할 수 있다. 대기할 수 없는 문맥에서는 즉시 할당할 수 없으면 실패를 반환한다. [오버커밋 정책](https://docs.kernel.org/mm/overcommit-accounting.html), [메모리 회수와 컴팩션](https://docs.kernel.org/admin-guide/mm/concepts.html#reclaim), [사용자 주소 접근 API](https://docs.kernel.org/kernel-hacking/hacking.html#copy-to-user-copy-from-user-get-user-put-user)
4. **잠들 수 있는지 확인**. 시스템 호출이나 장치 초기화처럼 잠들 수 있는 문맥에서는 메모리를 확보하는 동안 현재 태스크를 대기시킬 수 있다. 하드 인터럽트 핸들러, 인터럽트를 비활성화한 구간, 일반적인 스핀락 보호 구간에서는 잠들지 않는 할당 경로가 필요하다. 필요한 버퍼를 미리 확보하거나, 즉시 할당이 실패했을 때 실행할 경로를 함께 정한다. [커널의 실행 문맥](https://docs.kernel.org/kernel-hacking/hacking.html), [GFP 플래그와 회수 동작](https://docs.kernel.org/core-api/memory-allocation.html#gfp-flags-and-reclaim-behavior)

## 2. 크기와 주소 조건에 따른 할당 API

| 할당과 해제 | 할당 인자 | 주소와 용도 |
| --- | --- | --- |
| `kmalloc()` / `kfree()` (`<linux/slab.h>`) | 바이트 수, GFP 플래그 | 커널 가상 주소와 대응하는 물리 주소가 모두 연속된다. 작은 객체나 일반 버퍼를 빠르게 할당하는 데 쓴다. |
| `__get_free_pages()` / `free_pages()` (`<linux/gfp.h>`) | GFP 플래그, 페이지 차수 `order` | 물리적으로 연속된 `2^order`개의 페이지를 확보한다. 호출자는 시작 가상 주소와 할당 차수를 함께 보관한다. |
| `vmalloc()` / `vfree()` (`<linux/vmalloc.h>`) | 바이트 수 | 연속된 커널 가상 주소에 여러 물리 페이지를 매핑한다. CPU에서 사용할 큰 버퍼에 적합하며, 페이지를 모으고 가상 주소 매핑을 구성하는 비용이 든다. 할당은 잠들 수 있는 문맥에서 한다. |

`kmalloc()`과 `vmalloc()`은 양수 크기 요청에 성공하면 버퍼 시작 주소를, 실패하면 `NULL`을 반환한다. 대응하는 해제 함수에는 할당할 때 받은 시작 주소를 전달한다. 두 할당 함수가 반환하는 버퍼의 내용은 미초기화 상태다. 0으로 초기화된 버퍼가 필요하면 각각 `kzalloc()`이나 `vzalloc()`을 사용할 수 있다. `kmalloc()`의 크기 상한은 아키텍처와 커널 설정에 따라 달라지며, 큰 연속 물리 영역은 단편화의 영향도 받는다. `vmalloc()`의 할당 가능 크기는 가상 주소 공간과 사용 가능한 페이지 등으로 제한되며, 호출 도중 잠들 수 있다. [메모리 할당 API 선택](https://docs.kernel.org/core-api/memory-allocation.html#selecting-memory-allocator), [커널 메모리 관리 API](https://docs.kernel.org/core-api/mm-api.html)

`vmalloc()` 버퍼의 물리 배치를 확인해야 하면 `vmalloc_to_page()`로 각 가상 페이지에 대응하는 `struct page`를 찾을 수 있다. 이렇게 찾은 페이지는 버퍼를 뒷받침하는 RAM 페이지다. 커널의 직접 매핑 주소를 변환하는 `virt_to_phys()`를 적용할 수 있는 범위와 구분한다. [가상 주소 매핑 구현](https://github.com/torvalds/linux/blob/master/mm/vmalloc.c), [커널 주소 변환 규약](https://docs.kernel.org/driver-api/device-io.html)

### 2.1 GFP 플래그와 실패 처리

| 플래그 | 허용하는 동작과 사용 조건 |
| --- | --- |
| `GFP_KERNEL` | 잠들 수 있는 문맥에서 쓰는 일반 할당이다. 직접 메모리를 회수하는 과정에서 잠들 수 있고, 회수 후에도 조건을 만족하지 못하면 `NULL`이 돌아올 수 있다. |
| `GFP_NOWAIT` | 호출자가 직접 메모리를 회수하거나 대기할 수 없는 상황에 쓴다. 확보할 메모리가 없으면 실패를 반환한다. |
| `GFP_ATOMIC` | 대기할 수 없는 문맥에서 긴급한 요청이 일부 비상 예약분까지 사용할 수 있게 한다. 예약분이 있어도 요청을 충족할 수 없는 경우를 처리해야 한다. |
| `GFP_DMA` | 주소 지정 범위가 좁은 장치를 위해 특정 DMA 메모리 영역을 선택하는 플래그다. 장치에 전달할 DMA 주소는 DMA API로 얻는다. |

예를 들어 장치 초기화 중 통계 버퍼를 만들 때 `kzalloc(size, GFP_KERNEL)`이 `NULL`을 반환하면, 앞서 획득한 자원을 정리하고 `-ENOMEM`을 반환한다. 하드 인터럽트에서 즉시 확보할 수 없는 요청 정보는 처리 지연이나 누락을 허용하는지에 따라 미리 마련한 객체를 사용하거나 실패를 기록한다. [커널 메모리 할당 가이드](https://docs.kernel.org/core-api/memory-allocation.html)

### 2.2 페이지 차수 계산

`order`가 `0`, `1`, `2`이면 각각 한 페이지, 두 페이지, 네 페이지를 할당한다. `get_order(size)`는 양수인 `size` 바이트를 담을 수 있는 가장 작은 차수를 계산한다. 예를 들어 세 페이지 분량의 작업 공간에 `get_order(3 * PAGE_SIZE)`를 적용하면 차수 `2`가 나오므로 네 페이지를 요청한다. 최대 차수는 커널 버전과 빌드 설정에 따라 달라지고, 차수가 커질수록 물리적으로 연속된 블록을 확보하기 어려워진다. [차수 계산 구현](https://github.com/torvalds/linux/blob/master/include/asm-generic/getorder.h), [페이지 차수 제한](https://github.com/torvalds/linux/blob/master/include/linux/mmzone.h)

`__get_free_pages(gfp_mask, order)`는 성공하면 첫 페이지의 커널 가상 주소를 `unsigned long`으로 반환하고 실패하면 `0`을 반환한다. 성공한 블록은 사용을 마친 뒤 `free_pages(addr, order)`에 처음 받은 주소와 같은 차수를 넘겨 반환한다. `alloc_pages()`로 `struct page *`를 얻는 경우에는 `__free_pages()`가 짝을 이룬다. [페이지 할당기 구현](https://github.com/torvalds/linux/blob/master/mm/page_alloc.c), [페이지 해제 API](https://docs.kernel.org/core-api/mm-api.html#c.free_pages)

## 3. 메모리 풀의 예비 객체

메모리 풀은 메모리 압박 중에도 꼭 필요한 작업을 이어갈 수 있게 객체를 미리 확보한다. 예를 들어 블록 입출력 경로에서 요청을 마치는 데 필요한 기록 객체를 예비로 남겨 두면, 일반 할당에 실패해도 진행 중인 요청을 완료하고 자원을 반환할 수 있다. `min_nr`는 동시에 진행될 수 있는 요청과 각 요청이 반환되기까지 필요한 객체 수를 기준으로 정한다. [커널 메모리 풀 구현](https://github.com/torvalds/linux/blob/master/mm/mempool.c)

| API 또는 콜백 (`<linux/mempool.h>`) | 역할 |
| --- | --- |
| `mempool_create(min_nr, alloc_fn, free_fn, pool_data)` | 풀 관리 객체를 만들고 `min_nr`개의 예비 객체를 채운다. 성공하면 풀 주소를, 실패하면 `NULL`을 반환한다. 생성 중 잠들 수 있다. |
| `mempool_alloc_t` | `alloc_fn(gfp_mask, pool_data)`의 함수형이다. 객체를 새로 만들어 주소를 반환하고 실패하면 `NULL`을 반환한다. |
| `mempool_free_t` | `free_fn(element, pool_data)`의 함수형이다. 풀에서 더 이상 보관할 필요가 없는 객체를 실제로 해제한다. |
| `mempool_alloc(pool, gfp_mask)` | 설정한 할당 콜백으로 새 객체를 얻으려 시도하고, 실패하면 예비 객체를 꺼낸다. |
| `mempool_free(element, pool)` | 예비분이 부족하면 반환된 객체로 풀을 채우고, 이미 채워져 있으면 해제 콜백에 넘긴다. |
| `mempool_destroy(pool)` | 새 사용을 막고 빌린 객체를 모두 돌려받은 뒤 호출한다. 남은 예비 객체와 풀 관리 객체를 해제한다. |

할당 콜백은 풀 생성 때 설정한 `pool_data`를 이용해 객체의 크기나 종류를 결정한다. `mempool_alloc()`은 호출마다 크기를 받는 대신 그 풀에서 정한 종류의 객체 하나를 제공한다. 콜백에서 새 객체를 초기화할 수 있으며, 예비 객체에는 이전 사용 내용이 남을 수 있으므로 매번 필요한 필드를 사용 전에 초기화한다. [메모리 풀 API 선언](https://github.com/torvalds/linux/blob/master/include/linux/mempool.h), [메모리 풀 할당·반환 동작](https://docs.kernel.org/core-api/mm-api.html#memory-pools)

새 할당에 실패하고 예비 객체도 다 쓴 경우, `GFP_KERNEL`처럼 직접 회수가 허용된 요청은 객체가 돌아오기를 기다리거나 재시도할 수 있다. `GFP_ATOMIC`처럼 잠들 수 없는 요청은 `NULL`을 반환할 수 있다. 인터럽트에서 같은 풀을 사용한다면 GFP 플래그와 할당·해제 콜백 모두 그 문맥에서 잠들지 않도록 구성한다. [메모리 풀 구현](https://github.com/torvalds/linux/blob/master/mm/mempool.c)

## 4. 드라이버 상태를 저장하는 위치

| 선언과 수명 | 드라이버에서의 용도 |
| --- | --- |
| 함수 안의 일반 지역 변수 | 함수 호출 동안만 필요한 값에 사용한다. 컴파일러는 값을 현재 실행 문맥의 커널 스택이나 CPU 레지스터에 둘 수 있다. 호출마다 별도 값을 가지므로 호출 간 공유를 줄일 수 있다. |
| 함수 안의 `static` 변수 | 이름은 함수 안에서만 보이지만 객체와 값은 호출이 끝난 뒤에도 유지된다. 동시 호출은 같은 객체에 접근한다. |
| 파일 범위의 `static` 변수와 함수 | 변수는 모듈이 적재된 동안 유지되고, 변수와 함수의 이름은 해당 번역 단위 안에서만 참조할 수 있다. 다른 파일에서 같은 이름을 써도 외부 링크 이름이 충돌하지 않는다. |
| 외부 연결을 가진 함수와 변수 | 여러 파일에서 선언을 공유해 연결할 수 있다. 별도 모듈에서 참조하게 하려면 `EXPORT_SYMBOL()` 등으로 커널 심볼을 공개한다. |

파일 범위 객체의 크기와 상대 배치는 빌드 과정에서 정해지고, 모듈의 실제 주소는 적재와 재배치 과정에서 결정된다. 자동 지역 변수의 저장 위치는 각 호출에 따라 달라진다. 파일 범위의 `static`은 이름의 연결 범위를 제한하며, 로컬 심볼은 빌드 결과에 남을 수 있다. [커널 모듈 빌드와 공개 심볼](https://docs.kernel.org/kbuild/modules.html), [모듈 적재 구현](https://github.com/torvalds/linux/blob/master/kernel/module/main.c)

임시 계산에는 일반 지역 변수를 사용하고, 장치별 설정이나 대기열은 장치별 구조체에 둔다. 예를 들어 여러 장치의 요청 개수를 함수 내부 `static` 변수 하나에 저장하면 호출마다 같은 값에 접근한다. 장치별로 구분하려면 각 장치 객체에 카운터를 두고, 여러 CPU나 인터럽트가 같은 카운터를 수정한다면 락이나 원자 연산으로 갱신을 보호한다. [커널 락과 실행 문맥](https://docs.kernel.org/kernel-hacking/locking.html)

## 5. 플랫폼 사이에서 데이터 표현 맞추기

### 5.1 정수형과 구조체 배치

| 비트 수 | 부호 있는 커널 정수형 | 부호 없는 커널 정수형 | 사용자 공간 인터페이스의 정수형 |
| --- | --- | --- | --- |
| 8 | `s8` | `u8` | `__s8`, `__u8` |
| 16 | `s16` | `u16` | `__s16`, `__u16` |
| 32 | `s32` | `u32` | `__s32`, `__u32` |
| 64 | `s64` | `u64` | `__s64`, `__u64` |

커널 코드에서는 `<linux/types.h>`의 정수형을 쓸 수 있다. 장치의 필드나 사용자 공간 ABI처럼 폭을 고정해야 하는 곳에는 고정 폭 타입을 사용하고, 사용자 공간에 공개하는 구조체에서는 `__u32`처럼 UAPI에서 제공하는 이름을 사용한다. `long`이나 포인터처럼 32비트와 64비트 환경에서 폭이 달라질 수 있는 타입은 공유 구조체의 배치에 영향을 준다. 내부 계산용 `int`나 객체 크기를 나타내는 `size_t`처럼 의미에 맞는 일반 타입은 내부 코드에서 그대로 사용할 수 있다. [커널 정수형 정의](https://github.com/torvalds/linux/blob/master/include/linux/types.h), [ioctl ABI의 구조체 배치](https://docs.kernel.org/driver-api/ioctl.html#structure-layout)

컴파일러는 멤버의 정렬 조건을 만족시키기 위해 멤버 사이와 구조체 끝에 패딩을 넣을 수 있다. 프로토콜이 필드 오프셋을 고정하면 `__packed` 또는 `__attribute__((packed))`로 암시적 패딩을 줄여 그 배치에 맞출 수 있다. 이때 멤버가 자연 정렬 경계에서 벗어날 수 있으므로 멤버 주소를 일반 정수 포인터처럼 다루는 코드에 주의한다. 사용자 공간과 공유하는 구조체는 자연 정렬을 유지하면서 예약 필드로 패딩을 명시할 수 있다. [커널의 비정렬 메모리 접근](https://docs.kernel.org/core-api/unaligned-memory-access.html), [사용자 공간 구조체 호환성](https://docs.kernel.org/driver-api/ioctl.html#structure-layout)

### 5.2 바이트 순서와 비정렬 접근

리틀 엔디언은 가장 덜 중요한 바이트를 가장 낮은 주소에 놓고, 빅 엔디언은 가장 중요한 바이트를 가장 낮은 주소에 놓는다. 예를 들어 `0x4A7C`를 메모리에 저장하면 낮은 주소부터 리틀 엔디언은 `7C 4A`, 빅 엔디언은 `4A 7C` 순이다. `<asm/byteorder.h>`는 아키텍처에 맞는 바이트 순서 정의를 선택하고, 해당 헤더는 `__LITTLE_ENDIAN`이나 `__BIG_ENDIAN`을 정의한다. [리틀 엔디언 정의](https://github.com/torvalds/linux/blob/master/include/uapi/linux/byteorder/little_endian.h), [빅 엔디언 정의](https://github.com/torvalds/linux/blob/master/include/uapi/linux/byteorder/big_endian.h)

외부 형식의 `__le32`나 `__be32` 필드는 `le32_to_cpu()`나 `be32_to_cpu()`로 읽고, 내보낼 때는 `cpu_to_le32()`나 `cpu_to_be32()`로 변환한다. 이 함수들은 CPU와 외부 형식의 바이트 순서가 다를 때 필요한 바이트 교환을 수행한다. [바이트 순서 도우미 구현](https://github.com/torvalds/linux/blob/master/include/linux/byteorder/generic.h)

예를 들어 4바이트 값을 4의 배수가 아닌 주소에서 직접 읽으면 CPU에 따라 추가 비용이 들거나 예외가 발생한다. 컴파일러는 일반 객체의 정렬을 맞추지만, 수신한 바이트 배열의 필드 오프셋은 외부 형식이 결정한다. `<linux/unaligned.h>`의 `get_unaligned(ptr)`과 `put_unaligned(value, ptr)`는 일반 메모리에서 비정렬 읽기와 쓰기를 처리한다. 길이를 확인한 패킷에서 리틀 엔디언 필드를 읽을 때 `get_unaligned_le32()`를 쓰면 비정렬 접근과 바이트 순서 변환을 함께 처리할 수 있다. 쓰기에는 `put_unaligned_le32()`를 사용한다. [비정렬 접근의 영향](https://docs.kernel.org/core-api/unaligned-memory-access.html), [비정렬 접근 도우미 선언](https://github.com/torvalds/linux/blob/master/include/linux/unaligned.h)

## 6. 장치가 사용하는 주소

### 6.1 장치 레지스터와 MMIO

일부 아키텍처는 별도 I/O 포트 공간을 제공하며 `inb()`와 `outb()` 같은 함수로 접근할 수 있다. MMIO에서는 CPU 주소 공간의 일부가 장치 레지스터에 대응한다. 드라이버는 발견한 MMIO 자원을 `ioremap()` 등으로 매핑한 뒤 `void __iomem *`를 얻고, 레지스터 폭과 바이트 순서에 맞춰 `readl()`과 `writel()` 같은 접근 함수를 호출한다. 예를 들어 리틀 엔디언 32비트 상태 레지스터에는 `readl()`을, 빅 엔디언 32비트 레지스터에는 `ioread32be()`를 사용할 수 있다. 직접 `ioremap()`한 영역은 사용이 끝나면 `iounmap()`으로 해제한다. [리눅스의 장치 입출력 API](https://docs.kernel.org/driver-api/device-io.html)

레지스터는 읽기만 해도 상태가 바뀔 수 있어서 컴파일러가 읽기를 생략하거나 합치면 동작이 달라진다. `volatile`은 지정한 객체에 대한 컴파일러의 접근 최적화를 제한한다. MMIO에서 요구하는 접근 폭, 바이트 순서, 다른 입출력과의 순서는 커널의 장치 접근 함수와 매핑 규칙을 따른다. [커널에서의 `volatile`](https://docs.kernel.org/process/volatile-considered-harmful.html), [MMIO 접근 함수](https://docs.kernel.org/driver-api/device-io.html)

### 6.2 DMA 버퍼

CPU가 쓰는 가상 주소, RAM의 물리 주소, 장치에 넘기는 DMA 주소를 구분한다. 장치의 DMA 주소 폭과 전송 구간 제약을 확인한 뒤 DMA API에 장치 정보를 전달한다. IOMMU가 있다면 DMA 주소는 IOMMU를 거쳐 물리 주소로 변환될 수 있다. `GFP_DMA`가 선택하는 메모리 영역과 장치가 실제로 사용할 매핑은 별개의 조건이다. [DMA 주소와 장치의 주소 제약](https://docs.kernel.org/core-api/dma-api-howto.html)

장치와 계속 공유하는 버퍼는 `dma_alloc_coherent()`로 CPU가 사용할 포인터와 장치에 줄 `dma_addr_t`를 함께 얻고 `dma_free_coherent()`로 반환한다. 일시적인 전송은 적합한 버퍼를 `dma_map_single()`로 매핑한 뒤 `dma_mapping_error()`로 실패 여부를 확인한다. 전송이 끝나면 `dma_unmap_single()`로 매핑을 해제한다. `dma_map_single()`의 버퍼에는 물리적 연속성이 필요하다. 여러 조각을 지원하는 장치는 scatter-gather 목록을 `dma_map_sg()`로 매핑해 사용할 수 있다. `vmalloc()`의 연속 가상 주소 범위는 CPU용 버퍼로 취급한다. [DMA 할당과 매핑 절차](https://docs.kernel.org/core-api/dma-api-howto.html), [DMA API의 메모리 조건](https://docs.kernel.org/core-api/dma-api.html)
