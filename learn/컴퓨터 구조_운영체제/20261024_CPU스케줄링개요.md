# CPU 스케줄링 개요

한 CPU에 긴 작업과 짧은 작업이 들어왔을 때, 실행 순서와 선점 시점에 따라 첫 응답이 얼마나 달라지는지 비교한다. 우선순위를 정하는 방법과 여러 준비 큐를 사용하는 정책도 정리한다.

학습일 **2026-10-24**

## 1. 두 작업이 들어오는 시점으로 정책 비교하기

가상의 단일 CPU에서 미리보기 인덱스를 만드는 작업이 시각 0에 도착해 CPU를 7단위 사용하고, 파일 이름을 조회하는 작업이 시각 2에 도착해 CPU를 2단위 사용한다고 가정한다. 문맥 교환 시간과 입출력은 이 계산에서 생략한다.

| 정책 | 이 상황의 실행 순서 | 선택 기준 |
| --- | --- | --- |
| 최소 잔여 시간 우선(SRTF) | 인덱스 0~2, 조회 2~4, 인덱스 4~9 | 조회가 도착했을 때 필요한 2단위가 실행 중인 작업의 남은 5단위보다 작아 선점한다. |
| 라운드 로빈(RR), 할당 시간 3 | 인덱스 0~3, 조회 3~5, 인덱스 5~9 | 실행 중인 작업이 시간 한도를 채우면 준비 큐 뒤로 보낸다. 시각 8에는 인덱스만 남아 다시 선택된다. |
| 선입 선처리(FCFS) | 인덱스 0~7, 조회 7~9 | 준비 큐에 들어온 순서로 실행한다. 긴 작업 때문에 뒤의 짧은 작업도 오래 기다리는 호위 효과가 나타난다. |
| 최단 작업 우선(SJF), 비선점형 | 인덱스 0~7, 조회 7~9 | 시각 0에는 인덱스만 준비돼 있다. 두 작업이 동시에 준비돼 있었다면 예상 CPU 버스트가 짧은 조회를 먼저 실행한다. |

선점형 정책은 타임 슬라이스가 끝나거나 더 우선하는 작업이 준비됐을 때 CPU를 회수할 수 있다. 비선점형 정책에서는 현재 작업이 종료되거나 대기 상태로 들어가거나 자발적으로 양보할 때 다음 작업을 고른다. SRTF는 실행에 남은 시간을 기준으로 선점 여부를 결정한다. RR은 정해진 시간 한도를 사용하며, 한도가 짧으면 문맥 교환이 잦아지고 충분히 길면 FCFS와 비슷해진다. SJF와 SRTF는 실행 시간을 정확히 예측하기 어렵고, 짧은 요청이 계속 도착하면 긴 작업이 밀릴 수 있다.

## 2. 다음에 실행할 수 있는 작업을 구분하기

준비 큐에는 바로 실행할 수 있지만 CPU를 기다리는 작업이 있다. 디스크 읽기가 진행 중인 작업은 입출력 대기열에 머무르고 완료 신호가 오면 다시 준비 상태가 된다. 이때 운영체제가 모든 PCB를 매번 조사할 필요는 없다. 각 상태나 대기 원인에 해당하는 자료 구조를 관리할 수 있고, 준비 작업의 정렬 방식은 스케줄링 정책에 따라 정한다.

CPU에서 연속해 실행하는 구간을 CPU 버스트, 입출력을 요청하고 완료를 기다리는 구간을 입출력 버스트라고 한다. 입출력 집중 작업은 짧게 실행한 뒤 다시 기다리는 일이 많고, CPU 집중 작업은 계산을 오래 이어가는 경우가 많다. 입출력 작업이 깨어났을 때 빨리 실행하게 하면 응답 시간을 줄일 수 있다. 정책에 따라 문맥 교환 비용, 평균 대기 시간, 처리량과 작업 간 공정성도 함께 고려한다.

## 3. 우선순위를 적용하는 위치

| 방식 | 실행할 작업을 고르는 방법 |
| --- | --- |
| 우선순위 스케줄링 | 우선순위가 높은 작업부터 선택한다. 실행 중인 작업을 회수할지는 선점 설정에 따른다. |
| 다단계 큐(MLQ) | 작업 종류나 등급으로 큐를 배정한다. 배치 작업 큐에 FCFS를, 대화형 작업 큐에 RR을 적용하는 식으로 큐 내부 규칙을 정할 수 있다. 일반적인 모델에서 작업의 큐는 고정된다. |
| 다단계 피드백 큐(MLFQ) | 실행 이력을 보고 작업의 큐를 바꾼다. 예를 들어 할당 시간을 반복해 모두 소진하는 작업을 낮추고, 대기 시간이 긴 작업을 올리거나 일정 주기로 등급을 재설정할 수 있다. 큐별 시간과 이동 조건은 구현에 따라 다르다. |

상위 우선순위 작업만 계속 선택하면 낮은 우선순위 작업이 실행 기회를 얻지 못하는 기아가 발생할 수 있다. 오래 기다린 작업의 우선순위를 서서히 높이는 에이징은 이를 줄이는 방법이다.

리눅스에서는 `ps -el`의 `NI`와 `PRI`로 관련 값을 볼 수 있다. 일반 스케줄링의 nice 값은 `-20`부터 `19`까지이며, 낮을수록 CPU 배분에 유리한 가중치를 받는다. `nice -n 6 명령어`는 새 명령의 nice 값을 현재 값에서 조정하고, `renice -n 12 -p PID`는 실행 중인 프로세스의 값을 바꾼다. 변경 가능한 범위는 권한에 따라 다르다. 실시간 스케줄링의 우선순위는 별도 속성이다. [리눅스의 nice 설계](https://docs.kernel.org/6.10/scheduler/sched-nice-design.html), [리눅스 `nice(1)` 매뉴얼](https://man7.org/linux/man-pages/man1/nice.1.html)
