# 프로세스 동기화와 교착 상태

두 작업이 같은 상태를 갱신하거나 상대 작업의 자원을 기다릴 때 어떤 문제가 생기는지 살펴본다. 처리 결과를 일관되게 만드는 동기화와 실행이 멈추는 교착 상태를 하나의 작업 대기열 사례로 설명한다.

학습일 **2026-10-25**

## 1. 작업 대기열의 상태를 한 번에 갱신하기

여러 작업자가 같은 인쇄 대기열에서 맨 앞의 요청을 가져간다고 가정한다. 두 작업자가 요청 번호를 읽은 뒤 각각 제거하려 하면 같은 요청을 두 번 처리할 수 있다. 대기열·파일·공유 변수처럼 함께 접근하는 대상을 공유 자원이라고 한다. 읽기와 제거를 하나의 임계 구역으로 묶으면 작업 하나를 가져오는 동안 다른 작업자가 중간 상태를 보지 못한다. 실행 시점에 따라 결과가 달라지는 문제는 경쟁 상태다.

임계 구역에는 **상호 배제**가 필요하다. 또한 구역이 비었고 요청자가 있다면 진입 결정이 계속 미뤄지지 않는 **진행** 조건과, 요청한 작업자가 차례를 얻기 전 다른 작업자가 먼저 들어가는 횟수에 한계를 두는 **유한 대기** 조건을 고려한다. 동기화는 이런 공유 상태 보호와, 작업이 진행돼야 할 순서를 맞추는 데 쓰인다.

| 대기열에서 필요한 동작 | 사용할 수 있는 수단 |
| --- | --- |
| 요청 한 건의 조회와 제거를 함께 수행 | 뮤텍스로 잠금을 얻고 작업한 뒤 반납한다. 보통 잠금을 획득한 실행 흐름이 해제한다. 일반적인 뮤텍스는 대기자를 잠재울 수 있고, 스핀락은 잠금 상태를 반복해서 확인하며 기다린다. |
| 동시에 사용 가능한 출력 슬롯 수를 제한 | 카운팅 세마포의 허가 수를 슬롯 수로 시작한다. `wait`(`P`, `down`)에서 허가를 얻고, `signal`(`V`, `up`)에서 허가를 돌려준다. 두 연산의 허가 갱신은 원자적으로 처리한다. |
| 요청이 들어온 뒤에만 작업자 실행 | 허가 수가 0인 세마포에서 작업자를 기다리게 하고, 요청을 등록한 쪽이 `signal`로 깨운다. 이진 세마포는 값이 0 또는 1인 경우에 사용한다. |

모니터는 대기열 상태와 조작 연산을 같은 인터페이스에 두고 내부 접근을 직렬화하는 구조다. 대기열이 비었으면 작업자는 조건 변수의 `wait`를 호출한다. 대기하는 동안 연관된 잠금을 풀고, 돌아올 때 다시 획득한다. 요청을 넣는 쪽은 `signal` 또는 `notify`로 대기자를 깨울 수 있다. 깨어나는 동안 다른 작업자가 먼저 요청을 가져갈 수도 있으므로 `while`로 조건을 다시 검사한다. 진입 순서는 구현의 대기 정책에 따른다.

## 2. 서로의 자원 반납을 기다리는 경우

작업자 A가 출력 장치 하나를 점유한 상태에서 보관 잠금을 기다린다고 하자. 작업자 B가 그 잠금을 갖고 같은 출력 장치를 요청하면 두 작업자가 모두 멈춘다. 이 사례에는 자원을 한 작업자만 쓰는 **상호 배제**, 보유한 채 새 자원을 요청하는 **점유와 대기**, 가진 자원을 강제로 빼앗을 수 없는 **비선점**, 서로의 보유 자원을 잇는 **원형 대기**가 나타난다. 네 가지는 교착 상태의 필요조건이다. 어떤 시스템에서 이 조건들이 허용된다고 해서 모든 실행이 교착 상태에 이르는 것은 아니다.

자원 할당 그래프를 그릴 때 프로세스는 원, 자원 종류는 사각형으로 표현할 수 있다. 자원 종류 내부의 점은 각각의 인스턴스다. 요청은 프로세스에서 자원으로, 할당은 자원에서 프로세스로 향하는 화살표로 나타낸다. 모든 자원 종류의 인스턴스가 하나인 모델에서는 사이클이 교착 상태를 나타낸다. 인스턴스가 여럿이라면 사이클에 있는 작업이 다른 인스턴스를 반납받아 진행할 수도 있어, 사이클만으로 확정할 수 없다.

## 3. 자원 요청과 장애 대응을 설계하기

- **예방**은 교착에 필요한 조건을 깨는 방식이다. 위 사례에서 항상 보관 잠금을 먼저 얻도록 하면 요청 순서가 통일되어 원형 대기를 막을 수 있다. 공유 가능한 자원으로 바꾸거나, 필요한 자원을 한 번에 확보하게 하거나, 중간 상태를 복구할 수 있는 자원을 회수하는 방법도 있다. 전량을 미리 요구하면 자원 활용률이 떨어지고 대기가 길어질 수 있으며, 일부 장치는 동시 공유나 강제 회수가 어렵다.
- **회피**는 요청을 허용한 뒤에도 모든 작업을 차례로 완료할 순서가 남는지 검사한다. 먼저 끝날 작업이 돌려주는 자원을 다음 작업의 완료에 쓸 수 있다면 그 순서를 안전 순서열이라고 한다. 안전 순서열이 없으면 불안전 상태다. 그 시점에 이미 교착이 발생했는지는 실제 요청과 보유 상태를 확인해야 한다. 은행원 알고리즘이 대표적인 회피 방식이다.
- **검출과 회복**은 현재 요청·할당 상태에서 진행할 수 없는 작업을 찾아 자원을 회수하거나 작업을 종료한다. 중간 상태를 저장할 수 있다면 작업을 이전 시점으로 되돌려 다시 실행할 수 있다. 관련 작업을 한꺼번에 중단하면 빠르지만 손실이 크고, 하나씩 중단하면 중단할 대상을 줄이는 대신 매번 다시 검사해야 한다.
- **무시**는 발생 빈도와 피해가 낮고 대응 비용이 큰 상황에서 운영체제가 자동으로 해결하지 않는 선택이다. 오스트리치 알고리즘이라고도 한다.
