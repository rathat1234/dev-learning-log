# 리눅스 디바이스 파일 입출력과 커널 모듈의 심볼 링크 및 printk

커널이 `.ko` 모듈을 적재하면서 외부 심볼을 연결하고, 초기화 함수에서 드라이버를 등록하는 과정을 정리한다. 사용자 프로그램이 장치 노드를 만들어 파일 디스크립터로 입출력하는 방법과, 실패 원인을 `errno`와 커널의 `printk()` 로그에서 확인하는 방법도 함께 살펴본다.

학습일 **2026-11-08**

## 1. 드라이버의 역할과 모듈의 실행 환경

1. **디바이스 드라이버**는 하드웨어의 동작을 제어하고 커널에 장치 기능을 제공하는 코드다. **커널 모듈**은 실행 중인 커널에 기능을 적재하는 단위다. 드라이버는 커널 이미지에 내장하거나 모듈로 빌드할 수 있고, 파일 시스템과 통신 프로토콜도 모듈로 제공할 수 있다. [커널 모듈 설정](https://github.com/torvalds/linux/blob/master/kernel/module/Kconfig)
2. 내장 드라이버를 수정하면 변경된 커널 이미지를 빌드하고 그 이미지로 부팅해야 한다. 초기화에 문제가 생기면 부팅 단계에서 멈출 수도 있다. 적재 가능한 드라이버는 대상 커널에 맞춰 `.ko`를 다시 빌드하고, 이전 모듈의 사용이 끝났으면 제거한 뒤 재적재하여 시험할 수 있다. 배포판은 여러 장치를 지원하는 모듈을 함께 배포하고 각 시스템에서 필요한 것만 메모리에 적재할 수 있다. [외부 모듈 빌드](https://docs.kernel.org/kbuild/modules.html)
3. `.ko`는 커널 로더가 처리하는 ELF 객체다. 적재된 코드는 커널 모드에서 실행되고 커널 API를 통해 하드웨어와 내부 자료구조에 접근한다. 잘못된 주소 참조나 종료 조건 없는 루프는 시스템 전체에 영향을 줄 수 있다. 모듈 초기화 함수에도 별도의 프로세스 종료 동작이 없으므로, 오류를 반환하기 전에 이미 확보한 자원을 정리하고 대기나 지연에는 실행 문맥에 맞는 커널 API를 사용한다. [모듈 적재 시스템 호출](https://man7.org/linux/man-pages/man2/init_module.2.html), [커널 루틴의 실행 문맥](https://docs.kernel.org/kernel-hacking/hacking.html)

## 2. 심볼을 연결하는 방법

### 2.1 외부 참조와 콜백

1. 커널을 컴파일하고 링크한 뒤에도 모듈이 사용할 수 있도록 공개한 함수와 전역 변수의 심볼 정보가 남는다. 모듈을 적재할 때 로더가 외부 심볼 이름을 커널이나 먼저 적재된 모듈의 심볼과 대조하고, 적재된 메모리 주소에 맞게 참조를 재배치한다. 이 과정은 실행 중에 심볼을 연결한다는 점에서 동적 라이브러리의 링크와 유사하다. [모듈 적재와 재배치](https://man7.org/linux/man-pages/man2/init_module.2.html)
2. 모듈은 `EXPORT_SYMBOL()`로 공개된 심볼을 참조할 수 있다. `EXPORT_SYMBOL_GPL()`로 공개된 심볼을 사용하려면 로더가 모듈의 라이선스 표기를 GPL 호환으로 인식해야 한다. 예를 들어 한 모듈이 측정 데이터 변환 함수를 공개하고 다른 모듈이 이를 사용하면, 변환 함수를 제공하는 모듈이 먼저 적재되어야 한다. [커널 심볼 공개](https://docs.kernel.org/kernel-hacking/hacking.html)
3. 커널이 나중에 적재될 모듈의 함수를 호출할 때는 등록된 함수 포인터를 사용한다. 예를 들어 문자 장치 드라이버가 `struct file_operations`의 `.read`에 읽기 함수를 등록하면, 커널은 해당 장치 파일에 대한 `read()` 요청을 그 함수에 전달한다. 모듈의 직접 심볼 참조는 공개 심볼을 향하고, 반대 방향의 호출은 등록된 콜백을 통해 이뤄진다. 이처럼 모듈은 대상 커널이 정의한 구조체와 등록 규약에 맞춰 연결된다. [VFS의 파일 연산](https://docs.kernel.org/filesystems/vfs.html)

### 2.2 실행 중인 심볼과 빌드 시 버전 정보

| 확인 대상 | 읽을 수 있는 정보 |
| --- | --- |
| 구형 커널의 `/proc/ksyms` | 커널과 모듈이 공개한 심볼의 주소와 이름. 심볼 버전 관리가 켜진 구형 환경에서는 이름 뒤에 버전 식별자가 붙기도 했다. |
| 현재 커널의 `/proc/kallsyms` | 설정에 따라 커널과 적재된 모듈의 심볼 주소, 유형, 이름과 소속 모듈을 확인할 수 있다. 주소는 접근 권한과 보안 설정에 따라 가려진다. 이름이 보이는 심볼 중 모듈이 직접 참조할 수 있는 범위는 공개 여부로 결정된다. |
| 빌드 결과인 `Module.symvers` | 해당 빌드가 공개한 심볼, 제공 모듈, 공개 방식 및 `CONFIG_MODVERSIONS` 사용 시의 CRC를 확인할 수 있다. |

`CONFIG_MODVERSIONS`를 사용하면 커널 로더가 모듈이 기대하는 심볼의 CRC와 실행 중인 커널이 제공하는 CRC를 비교한다. 이름이 같아도 함수 선언과 관련 타입이 바뀌어 CRC가 다르면 적재가 거부될 수 있다. 커널 릴리스와 빌드 설정도 적재 호환성에 영향을 주므로, 모듈은 대상 커널의 빌드 트리를 기준으로 컴파일한다. [구형 심볼 조회 인터페이스](https://man7.org/linux/man-pages/man2/query_module.2.html), [현재 커널의 심볼 조회 구현](https://github.com/torvalds/linux/blob/master/kernel/kallsyms.c), [Kbuild 모듈 버전 관리](https://docs.kernel.org/kbuild/modules.html)

## 3. 모듈의 적재와 제거

### 3.1 사용자 공간 도구

| 명령 | 동작 |
| --- | --- |
| `insmod ./queue_limits.ko batch_limit=24` | 지정한 모듈 파일과 매개변수를 커널에 전달한다. 필요한 모듈이 따로 있으면 미리 적재되어 있어야 한다. |
| `depmod` | 설치된 모듈의 심볼 의존성을 분석해 `modules.dep`와 `modules.dep.bin` 등의 정보를 만든다. |
| `modprobe queue_limits batch_limit=24` | 실행 중인 커널에 맞춰 설치된 모듈을 이름이나 별칭으로 찾고, `modules.dep.bin`을 바탕으로 필요한 모듈부터 적재한다. 커널이 필요에 따라 모듈 적재를 요청할 때도 이 도구가 사용될 수 있다. |
| `lsmod` | `/proc/modules`를 읽어 모듈 이름, 메모리 크기, 사용 횟수와 사용 중인 모듈 이름을 표시한다. 사용 횟수에는 모듈 이름으로 표시되지 않는 참조도 반영될 수 있다. |
| `rmmod queue_limits` | 적재된 모듈을 이름으로 지정해 제거한다. |
| `modprobe -r queue_limits` | 대상 모듈을 제거하고, 의존 모듈 중 더 이상 쓰이지 않는 것도 제거할 수 있다. |

`insmod`와 `rmmod`는 사용자 공간 명령이다. 실패 시 명령의 오류와 `dmesg`를 함께 보면 누락된 심볼이나 버전 불일치처럼 커널이 거부한 이유를 찾을 수 있다. 모듈 경로 검색과 의존성 처리는 `modprobe`가 맡고, ELF 해석과 심볼 연결은 커널이 맡는다. [insmod(8)](https://man7.org/linux/man-pages/man8/insmod.8.html), [modprobe(8)](https://man7.org/linux/man-pages/man8/modprobe.8.html), [modules.dep(5)](https://man7.org/linux/man-pages/man5/modules.dep.5.html), [lsmod(8)](https://man7.org/linux/man-pages/man8/lsmod.8.html), [rmmod(8)](https://man7.org/linux/man-pages/man8/rmmod.8.html)

### 3.2 커널 내부에서 일어나는 일

1. **적재 요청을 검사한다.** 도구는 모듈 이미지 또는 열린 파일 디스크립터와 매개변수를 `init_module()` 또는 `finit_module()` 시스템 호출로 전달한다. 커널은 `CAP_SYS_MODULE` 권한, 같은 이름의 모듈이 이미 있는지, ELF 형식과 커널 호환성, 적용 중인 서명 정책 등을 검사한다. [init_module(2)](https://man7.org/linux/man-pages/man2/init_module.2.html), [커널 모듈 서명](https://docs.kernel.org/admin-guide/module-signing.html)
2. **모듈을 배치하고 연결한다.** 로더가 코드와 데이터에 필요한 커널 메모리를 마련하고 모듈을 관리 목록에 등록한다. 이어서 의존 모듈과 공개 심볼을 찾아 참조를 재배치한다. 내부의 `struct module`은 이름과 상태, 메모리 배치, 초기화·종료 함수, 공개 심볼과 참조 관계 등을 관리한다. 예외 처리나 디버깅에 쓰이는 정보는 커널 설정과 버전에 따라 달라진다. [모듈 자료구조](https://github.com/torvalds/linux/blob/master/include/linux/module.h), [커널 모듈 로더](https://github.com/torvalds/linux/blob/master/kernel/module/main.c)
3. **매개변수를 적용하고 초기화한다.** 커널은 전달받은 값을 선언된 타입으로 해석한 뒤 초기화 함수를 호출한다. 초기화 함수는 장치 등록과 자원 확보가 완료되면 `0`을 반환한다. 실패하면 앞서 확보한 자원을 역순으로 정리하고 `-EINVAL` 같은 음수 오류 값을 반환한다. 로더는 초기화에 성공한 모듈을 사용 가능 상태로 바꾸고 초기화 전용으로 표시된 메모리를 회수할 수 있다. [모듈 초기화 규약](https://docs.kernel.org/kernel-hacking/hacking.html), [커널 모듈 로더](https://github.com/torvalds/linux/blob/master/kernel/module/main.c)
4. **참조가 끝난 모듈을 제거한다.** 모듈 제거를 지원하는 커널에서 도구가 `delete_module()`을 호출하면, 커널은 권한과 모듈 상태, 다른 모듈의 의존성과 사용 중인 참조를 확인한다. 제거할 수 있으면 새 사용을 막고 종료 함수를 호출한다. 종료 함수에서 장치나 콜백 등록을 해제하고 대기 중인 작업을 정리한 뒤, 커널이 모듈 목록의 항목과 메모리를 회수한다. 강제 제거는 커널 설정에 따라 가능하며 사용 중인 코드에 대한 참조를 남겨 시스템을 불안정하게 만들 수 있다. [delete_module(2)](https://man7.org/linux/man-pages/man2/delete_module.2.html), [rmmod(8)](https://man7.org/linux/man-pages/man8/rmmod.8.html)

리눅스 2.6 이전에는 `create_module()`로 메모리를 예약하고 `query_module()`로 적재 목록, 주소, 심볼, 참조 관계를 조회할 수 있었다. 당시 도구는 이 정보를 이용해 사용자 공간에서 참조 주소를 재배치한 뒤 `init_module()`로 결과를 전달했다. 그 시기의 적재 주소 지도 출력, 미사용 모듈 자동 정리, 제거 가능 상태까지 대기 같은 기능은 당시의 도구와 커널 동작에 맞춰 해석해야 한다. [create_module(2)](https://man7.org/linux/man-pages/man2/create_module.2.html), [query_module(2)](https://man7.org/linux/man-pages/man2/query_module.2.html), [init_module(2)의 변경 이력](https://man7.org/linux/man-pages/man2/init_module.2.html)

## 4. 외부 모듈 작성과 매개변수

### 4.1 초기화 함수, 종료 함수와 빌드

모듈 헤더는 대상 커널의 소스와 빌드 결과에서 가져오며, 헤더 검색 경로와 컴파일 옵션은 Kbuild가 설정한다. `module_init()`으로 초기화 함수를, `module_exit()`로 제거 시 호출할 함수를 지정한다. 아래 예는 처리 한도 설정값과 로그에 붙일 이름을 적재 시점에 받아 초기화와 종료를 확인하는 모듈이다. [외부 모듈 빌드](https://docs.kernel.org/kbuild/modules.html), [커널 초기화 매크로](https://docs.kernel.org/kernel-hacking/hacking.html)

```c
// SPDX-License-Identifier: GPL-2.0-only
#include <linux/errno.h>
#include <linux/init.h>
#include <linux/module.h>
#include <linux/moduleparam.h>
#include <linux/printk.h>

static int batch_limit = 12;
static char *label = "bench";

module_param(batch_limit, int, 0444);
module_param(label, charp, 0);

static int __init queue_limits_init(void)
{
    if (batch_limit <= 0) {
        pr_err("queue_limits: batch_limit must be positive\n");
        return -EINVAL;
    }

    pr_info("queue_limits: %s enabled with limit %d\n", label, batch_limit);
    return 0;
}

static void __exit queue_limits_exit(void)
{
    pr_info("queue_limits: %s disabled\n", label);
}

module_init(queue_limits_init);
module_exit(queue_limits_exit);
MODULE_LICENSE("GPL");
```

같은 디렉터리의 `queue_limits.c`를 빌드하려면 `Makefile`에 `obj-m += queue_limits.o`를 적고, 대상 커널의 빌드 트리를 지정한다. 아래는 실행 중인 커널에 맞춰 빌드하는 경우다. `CONFIG_MODULES`가 켜진 커널의 설정과 헤더가 필요하다. `CONFIG_MODVERSIONS`를 쓰는 환경에서는 `modules_prepare`만 실행하면 `Module.symvers`가 만들어지지 않으므로, 대상 커널의 빌드 결과에 포함된 파일을 사용한다. [외부 모듈 빌드와 준비 조건](https://docs.kernel.org/kbuild/modules.html)

```sh
make -C "/lib/modules/$(uname -r)/build" M="$PWD" modules
```

소스의 SPDX 식별자는 적용된 라이선스를 표시한다. 적재 가능한 모듈은 `MODULE_LICENSE()`도 선언한다. 이 메타데이터를 로더와 도구가 GPL 호환 여부를 판단하는 데 사용한다. `GPL v2`는 `GPL`과 같은 의미의 기존 표기다. `Dual BSD/GPL`, `Dual MPL/GPL`처럼 이중 라이선스를 나타내는 값은 실제 배포 조건에 맞춰 사용한다. `Proprietary` 모듈을 적재하면 커널에 taint가 남고 GPL 전용 심볼에 연결할 수 없다. 모듈로 배포할 때 적용되는 라이선스는 소스에 명시된 조건을 따른다. [리눅스 커널의 라이선스 표기 규칙](https://docs.kernel.org/process/license-rules.html)

### 4.2 값이 전달되는 시점과 형식

1. 모듈 매개변수는 적재 시 코드의 기본값을 덮어쓴다. 장치의 버퍼 한도나 동작 모드 같은 초기 설정에 쓸 수 있다. 자동 탐색이 어려운 장치는 I/O 포트나 IRQ 번호를 설정값으로 받는 경우도 있었다. 모듈은 `insmod` 또는 `modprobe`의 `이름=값` 인자로 값을 받으며, 내장 드라이버는 부트로더가 넘기는 커널 명령줄의 `모듈명.이름=값` 형태로 지정할 수 있다. [커널 명령줄 매개변수](https://docs.kernel.org/admin-guide/kernel-parameters.html), [모듈 매개변수 선언](https://github.com/torvalds/linux/blob/master/include/linux/moduleparam.h)
2. `module_param(변수, 타입, 권한)`은 입력의 변환 방법과 sysfs 노출 권한을 정한다. 정수형은 `short`, `ushort`, `int`, `uint`, `long`, `ulong` 등이 있고, 문자열은 `charp`, 불리언은 `bool` 또는 반전 동작을 하는 `invbool`로 선언할 수 있다. 예를 들어 `int`에는 `24`, `030`, `0x18`을 넣어 같은 값을 전달할 수 있다. 변환 단계에서 형식과 자료형 범위를 확인하고, 양수만 허용하는 것과 같은 기능상의 제약은 초기화 코드에서도 검사한다. [커널의 매개변수 파서](https://github.com/torvalds/linux/blob/master/kernel/params.c)
3. 문자열에 공백이 있으면 `'label="queue check"'`처럼 인용할 수 있다. 바깥의 작은따옴표는 셸에서 인자를 하나로 묶고, 안쪽의 큰따옴표는 커널이 공백까지 값으로 읽게 한다. 배열은 `module_param_array()`로 선언하고 `channels=2,5,8`처럼 쉼표로 구분해 앞에서부터 전달한다. 전달한 요소 수를 변수로 받을 수 있다. 각 항목은 순서대로 파싱되므로, 정수 배열에 `2,,8`을 전달하면 중간의 빈 항목에서 오류가 발생한다. [커널 매개변수의 인용 규칙](https://docs.kernel.org/admin-guide/kernel-parameters.html), [배열 매개변수 선언](https://github.com/torvalds/linux/blob/master/include/linux/moduleparam.h), [커널의 매개변수 파서](https://github.com/torvalds/linux/blob/master/kernel/params.c)
4. 권한 `0`은 적재 시 매개변수를 받을 수 있지만 sysfs에 파일을 만들지 않는다. `0444`는 `/sys/module/<모듈명>/parameters/`에서 읽을 수 있고, `0644`는 소유자에게 쓰기 권한도 준다. 실행 중 쓰기를 허용하면 값이 바뀌는 순간에도 코드가 안전하게 동작하도록 설계해야 한다. [모듈 매개변수와 sysfs 권한](https://github.com/torvalds/linux/blob/master/include/linux/moduleparam.h)

## 5. 사용자 공간에서 디바이스 파일 다루기

### 5.1 장치 번호와 `mknod()`

문자·블록 장치 노드는 종류와 주요 번호(major), 부 번호(minor)를 담는다. 주요 번호는 보통 장치 종류나 드라이버가 관리하는 번호 범위를 가리키고, 부 번호는 그 범위 안에서 장치 인스턴스나 인터페이스를 구분하는 데 쓰인다. 커널이 장치 모델에 등록한 노드는 `devtmpfs`에서 자동으로 만들어질 수 있고, `udev` 같은 사용자 공간 관리자가 권한과 심볼릭 링크를 설정할 수 있다. 수동으로 만들 때는 이미 등록된 장치 번호를 확인한 뒤 `mknod` 명령 또는 `mknod()`를 사용한다. 노드의 생성과 드라이버의 등록은 별개의 단계다. [devtmpfs 커널 설정](https://github.com/torvalds/linux/blob/master/drivers/base/Kconfig), [mknod(1)](https://man7.org/linux/man-pages/man1/mknod.1.html), [mknod(2)](https://man7.org/linux/man-pages/man2/mknod.2.html)

| `mknod(path, mode, dev)` 인자 | 의미 |
| --- | --- |
| `const char *path` | 생성할 노드의 경로 |
| `mode_t mode` | `S_IFCHR`(문자 장치) 또는 `S_IFBLK`(블록 장치)와 접근 권한 비트를 `\|`로 결합한 값 |
| `dev_t dev` | `makedev(major_id, minor_id)`로 구성한 장치 번호. `major()`와 `minor()`로 각 번호를 얻을 수 있다. |

`S_IRWXU`와 `S_IRWXG`는 각각 소유자와 그룹에 읽기·쓰기·실행 비트를 모두 준다. 읽기와 쓰기만 지정할 때는 `0660`이나 `S_IRUSR | S_IWUSR | S_IRGRP | S_IWGRP`를 사용할 수 있다. 상위 디렉터리에 기본 ACL이 없으면 권한은 프로세스의 `umask`로 제한된다. 문자·블록 노드 생성에는 `CAP_MKNOD` 권한이 필요하며, 같은 경로에 항목이 이미 있으면 `EEXIST`로 실패한다. [mknod(2)](https://man7.org/linux/man-pages/man2/mknod.2.html), [makedev(3)](https://man7.org/linux/man-pages/man3/makedev.3.html)

```c
#include <sys/stat.h>
#include <sys/sysmacros.h>

int create_capture_node(const char *path, unsigned int major_id,
                        unsigned int minor_id)
{
    return mknod(path, S_IFCHR | 0660, makedev(major_id, minor_id));
}
```

이 예에서 `mknod()`는 성공하면 `0`, 실패하면 `-1`을 반환하고 `errno`를 설정한다. 같은 문자 장치를 셸에서 만들려면 등록된 번호를 확인한 후 `mknod -m 0660 "$node" c "$major_id" "$minor_id"`처럼 지정한다. `c`는 문자 장치, `b`는 블록 장치다. [mknod(2)](https://man7.org/linux/man-pages/man2/mknod.2.html), [mknod(1)](https://man7.org/linux/man-pages/man1/mknod.1.html)

### 5.2 파일 디스크립터를 사용하는 호출

| 호출과 반환 타입 | 헤더 | 인자와 동작 | 성공 시 반환값 |
| --- | --- | --- | --- |
| `int open(path, flags[, mode])` | `<fcntl.h>` | 경로를 열고 `O_RDONLY`, `O_WRONLY`, `O_RDWR` 중 하나를 선택한다. 장치가 지원하면 `O_NONBLOCK`을 함께 쓴다. 이미 생성된 노드를 열 때는 `mode`를 생략한다. | `0` 이상의 fd |
| `ssize_t read(fd, buf, count)` | `<unistd.h>` | 최대 `count`바이트를 읽어 `buf`에 저장한다. | 실제 읽은 바이트 수. `0`은 일반적으로 EOF를 뜻하며 장치의 읽기 규약을 확인한다. |
| `ssize_t write(fd, buf, count)` | `<unistd.h>` | `buf`에서 최대 `count`바이트를 장치에 전달한다. | 실제 받아들인 바이트 수 |
| `off_t lseek(fd, offset, whence)` | `<unistd.h>` | 장치가 지원하면 시작(`SEEK_SET`), 현재(`SEEK_CUR`), 끝(`SEEK_END`)을 기준으로 위치를 바꾼다. | 이동 후 오프셋 |
| `int ioctl(fd, request, ...)` | `<sys/ioctl.h>` | 장치 인터페이스가 정의한 요청 번호와 필요시 추가 인자를 전달한다. 예를 들어 읽기 모드나 샘플링 설정을 바꿀 수 있다. | 보통 `0`. 일부 요청은 별도의 음이 아닌 값을 반환한다. |
| `int fsync(fd)` | `<unistd.h>` | 지원하는 파일이나 장치에 보류된 쓰기의 동기화를 요청한다. 장치에서의 동작은 드라이버가 정의한다. | `0` |
| `int close(fd)` | `<unistd.h>` | fd를 해제한다. 같은 열린 파일에 대한 마지막 참조가 닫히면 해당 열린 파일의 자원도 해제된다. | `0` |

위 호출들은 실패하면 `-1`을 반환하고 `errno`를 설정한다. `read()`나 `write()`가 요청보다 적은 양을 처리하면 반환값만큼 버퍼 위치를 옮기고 장치 규약에 따라 나머지를 처리한다. 비블로킹 모드에서 현재 처리할 수 없는 요청은 `EAGAIN`을 반환할 수 있다. `write()`에서 성공으로 집계한 바이트가 실제 장치에 반영되는 시점은 버퍼링 및 동기화 방식에 달려 있다. [open(2)](https://man7.org/linux/man-pages/man2/open.2.html), [read(2)](https://man7.org/linux/man-pages/man2/read.2.html), [write(2)](https://man7.org/linux/man-pages/man2/write.2.html), [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)

위치 이동이 없는 장치에서는 `lseek()`가 `ESPIPE` 등으로 실패할 수 있고, 지원하지 않는 `ioctl()` 요청은 일반적으로 `ENOTTY`로 처리한다. 리눅스의 `close()`는 실패를 반환하는 경우에도 fd가 이미 해제되어 있을 수 있다. 같은 번호로 다시 호출하면 다른 스레드가 그사이 새로 연 파일을 닫을 수 있다. [lseek(2)](https://man7.org/linux/man-pages/man2/lseek.2.html), [커널의 ioctl 인터페이스](https://docs.kernel.org/driver-api/ioctl.html), [close(2)](https://man7.org/linux/man-pages/man2/close.2.html)

### 5.3 `errno`와 `perror()`

`errno`는 실패 원인을 코드로 담고, `<stdio.h>`의 `perror(const char *s)`는 전달한 작업 이름과 현재 `errno`에 해당하는 설명을 표준 오류에 출력한다. 예를 들어 `create_capture_node()`가 `-1`을 반환하면 곧바로 `perror("capture node creation")`를 호출할 수 있다. 후속 호출이 `errno`를 바꿀 수 있으므로 오류별 분기에도 값을 사용할 경우 먼저 복사해 둔다. 성공 여부는 호출의 반환값을 기준으로 판단한다. [perror(3)](https://man7.org/linux/man-pages/man3/perror.3.html), [errno(3)](https://man7.org/linux/man-pages/man3/errno.3.html)

응용 프로그램은 `<errno.h>`의 이름으로 오류를 비교하고, 드라이버의 콜백은 해당 규약에 따라 `-EINVAL`, `-EIO`, `-ENODEV` 같은 음수 오류 값을 반환한다. 잘못된 인자, 입출력 실패, 장치 부재처럼 의미가 맞는 값을 고르면 응용 프로그램이 원인에 따라 대응할 수 있다. 구체적인 발생 조건은 드라이버에 따라 달라지므로 대상 버전의 구현과 인터페이스 문서를 확인한다. [커널의 ioctl 오류 규약](https://docs.kernel.org/driver-api/ioctl.html), [errno(3)](https://man7.org/linux/man-pages/man3/errno.3.html)

## 6. `printk()`로 초기화와 입출력 추적하기

### 6.1 메시지의 레벨과 콘솔 출력

`printk()`는 `printf()`와 비슷하게 형식 문자열을 받는다. `printk(KERN_INFO "capture queue ready\n");`처럼 레벨 매크로를 문자열 앞에 붙이거나 `pr_info()`처럼 레벨이 정해진 함수를 사용한다. 접두사를 생략하면 커널에 설정된 기본 메시지 레벨이 적용된다. 독립적인 메시지는 `\n`으로 끝내면 한 줄의 로그로 구분하기 쉽다. [printk 메시지 기록](https://docs.kernel.org/core-api/printk-basics.html)

| 값 | 레벨 | 의미 |
| --- | --- | --- |
| 0 | `KERN_EMERG` | 시스템을 사용할 수 없는 긴급 상태 |
| 1 | `KERN_ALERT` | 즉시 조치가 필요한 상태 |
| 2 | `KERN_CRIT` | 치명적인 상태 |
| 3 | `KERN_ERR` | 오류 |
| 4 | `KERN_WARNING` | 경고 |
| 5 | `KERN_NOTICE` | 주목할 정상 상태나 변화 |
| 6 | `KERN_INFO` | 일반 동작 정보 |
| 7 | `KERN_DEBUG` | 디버깅 정보 |

로그는 커널 링 버퍼에 기록되고, 일반적으로 메시지의 레벨 값이 현재 콘솔 임계값보다 작으면 콘솔에도 표시된다. `/proc/sys/kernel/printk`의 첫 번째 값이 현재 콘솔 임계값이고, `dmesg -n`으로도 조정할 수 있다. 콘솔은 부팅 설정과 장치에 따라 화면의 가상 터미널이나 직렬 포트가 될 수 있고, 여러 콘솔이 설정될 수도 있다. [printk 메시지 기록](https://docs.kernel.org/core-api/printk-basics.html), [리눅스 직렬 콘솔](https://docs.kernel.org/admin-guide/serial-console.html), [dmesg(1)](https://man7.org/linux/man-pages/man1/dmesg.1.html)

### 6.2 링 버퍼 조회와 로그 보관

커널 링 버퍼는 크기가 제한된 순환 저장소다. 새 로그가 버퍼를 채우면 가장 오래된 기록부터 덮어쓴다. `CONFIG_LOG_BUF_SHIFT`는 버퍼 크기의 설정 기준을 2의 거듭제곱으로 표현하며, 부팅 시 `log_buf_len=`으로 크기를 지정할 수 있다. 콘솔에 출력하거나 로그 수집기가 읽은 메시지도 링 버퍼에 남아 있으면 다시 조회할 수 있다. [커널 로그 버퍼 설정](https://docs.kernel.org/admin-guide/kernel-parameters.html), [커널 로그 조회 인터페이스](https://man7.org/linux/man-pages/man2/syslog.2.html)

| 조회 방법 | 동작 |
| --- | --- |
| `dmesg` | 커널 링 버퍼에 남은 메시지를 조회한다. |
| `dmesg -w` | 기존 메시지를 출력하고 새 메시지가 들어올 때마다 이어서 보여준다. `Ctrl+C`로 종료한다. |
| `dmesg -c` | 메시지를 출력한 뒤 이후의 일반 조회에서 그 기록을 제외하도록 기준 위치를 옮긴다. |
| `/dev/kmsg` | 커널 로그를 사용자 공간에서 읽는 인터페이스다. 읽는 프로세스마다 읽기 위치가 따로 관리된다. |
| `/proc/kmsg` | 권한이 필요한 기존 로그 스트림이다. 메시지를 소비하는 방식이므로 로그 데몬과 동시에 읽으면 기록이 누락될 수 있다. |
| `journalctl -k` | systemd 환경에서 저널이 수집한 현재 부팅의 커널 로그를 조회한다. |

기존의 `klogd`는 커널 메시지를 읽어 `syslogd` 등에 전달했다. `syslogd`는 설정에 따라 커널 메시지와 응용 프로그램의 메시지를 `/var/log/messages` 같은 파일에 기록했다. systemd 환경에서는 `systemd-journald`가 커널 로그를 수집하며, 재부팅 뒤에도 남는지는 저장 설정에 달려 있다. 링 버퍼 조회의 허용 범위는 `dmesg_restrict` 같은 시스템 설정에도 영향을 받는다. [dmesg(1)](https://man7.org/linux/man-pages/man1/dmesg.1.html), [/proc/kmsg(5)](https://man7.org/linux/man-pages/man5/proc_kmsg.5.html), [/dev/kmsg ABI](https://www.kernel.org/doc/Documentation/ABI/testing/dev-kmsg), [커널 로그 수집의 이전 방식](https://www.kernel.org/doc/mirror/ols2007v2.pdf), [journald.conf](https://www.freedesktop.org/software/systemd/man/latest/journald.conf.html), [journalctl](https://www.freedesktop.org/software/systemd/man/latest/journalctl.html)

인터럽트나 빈번한 입출력 경로에서 매번 로그를 남기면 문자열 형식화와 버퍼 기록, 콘솔 출력 비용 때문에 처리 타이밍이 달라질 수 있다. 초기화나 상태 전환에 로그를 남기고, 반복되는 오류는 `pr_warn_ratelimited()` 같은 빈도 제한을 적용하면 원인을 추적하면서 로그 양을 줄일 수 있다. [printk와 성능에 민감한 경로](https://docs.kernel.org/core-api/printk-basics.html)

## 7. 초기화부터 종료까지 확인하는 순서

1. 모듈의 적재와 제거가 가능한 리눅스 테스트 환경에서 현재 커널용으로 `queue_limits.ko`를 빌드하고 `dmesg -w`를 열어 둔다.
2. `insmod ./queue_limits.ko batch_limit=24 'label="queue check"'`로 적재한다. `lsmod`에서 모듈이 표시되는지, 초기화 로그와 `/sys/module/queue_limits/parameters/batch_limit`에 기대한 값이 나오는지 확인한다.
3. `rmmod queue_limits`로 예제 모듈을 제거하고 종료 로그와 `lsmod`를 확인한다. 이어서 `insmod ./queue_limits.ko batch_limit=0`을 실행하면, 초기화 함수가 `-EINVAL`을 반환하고 적재가 실패하는 흐름을 확인할 수 있다.
4. 장치를 등록하는 모듈을 시험할 때는 적재 후 노드의 종류와 장치 번호를 확인한다. 사용자 프로그램의 `open()` 반환값, 실제 전송 길이와 실패 시의 `errno`를 커널 로그의 발생 시점과 대조한다. 시험을 끝내면 장치 fd나 의존 모듈의 참조를 정리하고 드라이버를 제거한다.
