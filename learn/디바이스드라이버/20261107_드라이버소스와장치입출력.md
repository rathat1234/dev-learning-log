# 드라이버 소스 구조와 장치 입출력

장치 식별 정보로 리눅스 드라이버 소스와 빌드 설정을 찾는 방법을 정리한다. 스트림 입출력과 파일 디스크립터 기반 입출력을 비교하고, 장치 요청의 블로킹, 부분 전송, 오류 처리도 다룬다.

학습일: 2026-11-07

## 1. 리눅스 드라이버 소스 구조

1. 커널 소스는 하드웨어 유형과 기능별 하위 시스템을 중심으로 구성된다.
2. 대표적인 디렉터리는 다음과 같다.
   - `drivers/base/`: 디바이스 모델과 드라이버 공통 기반
   - `drivers/char/`, `drivers/block/`: 문자·블록 장치 관련 코드
   - `drivers/input/`, `drivers/i2c/`, `drivers/usb/`: 입력 장치와 통신 버스
   - `drivers/net/`, `drivers/media/`, `drivers/mtd/`: 네트워크, 영상, 플래시 메모리
   - `drivers/pci/`, `drivers/tty/`, `drivers/gpu/drm/`: PCI, 터미널·시리얼, 그래픽
   - `sound/`: 사운드 하위 시스템
3. 드라이버 경로는 커널 버전에 따라 달라진다. 예전 커널의 `drivers/ide/`, `drivers/ieee1394/`, `drivers/char/drm/`에 해당하는 구현을 찾을 때는 분석 대상 버전의 소스 트리를 확인한다.

## 2. 원하는 드라이버 소스 찾기

1. 장치 식별
   - PCI 장치: `lspci -nn`으로 벤더·디바이스 ID 확인
   - USB 장치: `lsusb`로 VID·PID 확인
   - 임베디드 장치: SoC 문서, Device Tree의 `compatible`, 버스 정보 확인
2. 커널 소스 검색
   - `grep -R -n '모델명' drivers/`
   - 필요하면 ID, `compatible` 문자열, 드라이버 함수명으로 검색
3. 빌드 연결 관계 추적
   - `Kconfig`: 드라이버 설정 항목과 의존성 확인
   - `.config`: 현재 설정 활성화 여부 확인
   - `Makefile`: `obj-$(CONFIG_...)`와 소스 파일의 연결 확인
4. 드라이버가 없다면 유사 칩셋의 지원 여부와 데이터시트를 비교한 뒤 신규 구현 가능성을 검토한다.

## 3. 디바이스 파일의 역할

1. 리눅스는 많은 장치에 `/dev`의 장치 파일을 통해 접근하는 인터페이스를 제공한다. 모든 하드웨어가 반드시 개별 `/dev` 파일을 갖는 것은 아니다.
2. 장치 파일은 하드웨어 자체나 일반 데이터 저장 파일이 아니라, 커널의 장치 인터페이스를 식별하는 특수 파일이다.
3. 문자·블록 장치 파일에는 주요 번호(major)와 부 번호(minor)가 있으며, 커널이 해당 장치를 찾아 입출력 요청을 처리하는 데 사용한다.
4. 직접 생성해야 할 경우 등록된 장치 번호를 확인한 후 `mknod`를 사용한다. 보통은 `devtmpfs`와 `udev`가 장치 노드를 관리한다.
5. 장치 노드의 존재만으로 드라이버가 정상 등록되었거나 실제 하드웨어가 동작한다고 보장할 수는 없다.

## 4. 스트림 입출력과 저수준 입출력

1. 스트림 입출력: `fopen()`, `fread()`, `fwrite()`, `fclose()` 등. 사용자 공간의 `FILE` 객체를 이용하며, 일반적으로 stdio 버퍼링과 형식화 기능을 제공한다.
2. 저수준 입출력: `open()`, `read()`, `write()`, `close()` 등. 파일 디스크립터(fd)로 접근하며, stdio의 사용자 공간 버퍼를 거치지 않는다.
3. 장치 제어에서는 호출 시점과 전송량을 명확히 관리하기 위해 저수준 인터페이스를 주로 사용한다.
4. 단, `read()`·`write()` 호출이 곧바로 물리 하드웨어에 반영된다는 뜻은 아니다. 커널·드라이버·장치 내부 버퍼의 동작은 구현에 달려 있다.
5. 사용자 공간의 `FILE`과 커널 내부의 `struct file`은 서로 다른 구조다.

## 5. 주요 시스템 호출

1. `open(path, flags)`: 장치 파일 열기. 성공 시 `fd >= 0`, 실패 시 `-1` 반환 및 `errno` 설정
2. `close(fd)`: 파일 디스크립터 닫기. 자원을 해제하고 반환값으로 오류를 확인할 수 있다.
3. `read(fd, buf, count)`: 최대 `count`바이트 읽기. 실제 처리한 바이트 수를 반환한다.
4. `write(fd, buf, count)`: 최대 `count`바이트 쓰기. 실제 처리한 바이트 수를 반환한다.
5. `lseek(fd, offset, whence)`: 파일 위치 이동. 장치가 위치 이동을 지원하는 경우에만 유효하다.
6. `ioctl(fd, request, arg)`: `read()`·`write()`로 표현하기 어려운 명령과 설정 처리. 명령의 의미는 해당 인터페이스에 따라 달라진다.
7. `fsync(fd)`: 지원하는 파일·장치에서 보류된 데이터의 동기화를 요청한다. 구체적 동작은 구현에 따라 다르다.

## 6. 블로킹과 오류 처리

1. 기본 입출력은 장치 상태에 따라 대기할 수 있으며, 지원하는 장치에 `O_NONBLOCK`을 적용하면 준비되지 않은 요청에 대해 `EAGAIN` 등이 반환될 수 있다.
2. `read()`·`write()`의 반환값은 요청한 `count`보다 작을 수 있으므로 부분 읽기·쓰기를 처리해야 한다.
3. 실패 시 `errno`를 확인하고, `EINTR`(신호에 의한 중단), `EAGAIN`(현재 처리 불가), 장치별 오류를 구분한다.
4. 일반적인 장치 파일은 명확한 EOF나 파일 위치 개념이 없을 수 있다. `lseek()`의 `SEEK_SET`·`SEEK_CUR` 선택도 장치 구현과 목적에 맞춘다.

## 7. 장치 입출력에서 확인할 동작

1. **devfs**: 역사적 장치 파일 시스템이며 리눅스 2.6.18에서 제거되었다. 현대 리눅스는 주로 `devtmpfs`와 사용자 공간의 `udev`를 사용한다.
2. **장치 파일만 사용**: 모든 하드웨어가 `/dev` 파일로 제공되지는 않는다. 네트워크 인터페이스 등의 접근 방식은 다르다.
3. **스트림 입출력 금지**: 장치에 stdio를 기술적으로 사용할 수 없는 것은 아니다. 버퍼링 때문에 제어 타이밍이 중요한 장치에는 저수준 입출력이 적합하다.
4. **저수준 쓰기는 즉시 기록**: stdio 버퍼를 우회할 뿐, 실제 장치 반영·영구 저장 시점을 보장하지 않는다.
5. **`ioctl()`은 장치 파일 전용**: 장치 제어에 널리 사용되지만 파일 시스템 등 다른 종류의 파일에도 ioctl 명령이 존재한다.
6. **`SEEK_CUR` 우선 사용**: 보편적인 권장 규칙이 아니다. 장치에서 위치 이동 지원 여부와 각 기준점의 의미를 먼저 확인한다.

## 8. 실습 점검 순서

1. `lspci -nn`, `lsusb` 등으로 장치 정보 확인
2. 커널 소스의 `Kconfig` 및 `Makefile`에서 드라이버 설정과 소스 찾기
3. `/dev`의 장치 노드와 `/proc/devices`의 등록 상태 확인
4. `open()` 반환값 및 `errno` 확인
5. `read()`·`write()`의 실제 처리 길이, 블로킹 여부, 필요시 `ioctl()` 동작 점검
