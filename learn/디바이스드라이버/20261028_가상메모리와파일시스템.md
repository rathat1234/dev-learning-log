# 커널과 드라이버 개요

- 학습일: 2026-10-31
- 분류: 시스템 소프트웨어 / 커널 I/O 기초
- 정리 기준: 과거 커널 교재의 개념을 현재 커널 문서에 맞게 재해석

## 1. 리눅스 커널과 운영체제

1. **리눅스(Linux)**는 운영체제의 핵심인 **커널**이다. GNU 도구를 비롯한 사용자 공간 소프트웨어와 결합해 완전한 운영 환경을 구성한다.
2. 커널의 주요 역할은 **프로세스·스케줄링, 메모리, 파일 시스템, 장치, 네트워크, 보안** 관리다.
3. 리눅스는 **모놀리식 커널**이지만 기능을 **로드 가능한 모듈(.ko)**로 확장할 수 있다.
4. 주요 특징: 가상 메모리, VFS, 멀티스레드, SMP/NUMA, 커널 선점 설정, 다양한 CPU 아키텍처 지원. 일부 아키텍처에서는 **MMU가 없는 환경**도 지원한다.
5. GPL-2.0 기반의 오픈소스로서 라이선스 조건을 준수하면 소스 코드를 수정·재배포할 수 있다.
6. **안정성이 목적이라면 '최신 하드웨어보다 한 단계 낮은 제품'을 무조건 선택하기보다**, 장기 지원 커널, 드라이버 검증, 보안 업데이트 및 실제 테스트 결과를 우선 확인한다.

## 2. 커널 버전과 모듈 호환성

1. 모듈은 실행 중인 커널에 기능을 추가하는 방식이다. 빌드에 포함된 드라이버와 동적 적재되는 드라이버는 **구현·배포 방식의 차이**다.
2. 모듈은 커널 내부 API/ABI가 안정적으로 고정되지 않아, 커널 버전·설정·빌드 환경·외부 심볼 차이에 영향을 받는다.
3. 버전 문자열이 같아도 호환이 보장되지 않으며, 다르다고 언제나 절대 불가능한 것도 아니다. 실제로는 `vermagic`, 사용 심볼, `CONFIG_MODVERSIONS` 등을 확인해야 한다.
4. 모듈 적재 실패 시 **커널 릴리스 → 모듈 정보 → 커널 로그** 순서로 점검한다.

```bash
uname -r
modinfo ./example.ko | grep vermagic
sudo dmesg | tail -n 30
```

## 3. 커널 소스 트리에서 자주 찾는 위치

| 경로 | 주요 내용 |
| --- | --- |
| `Documentation/` | 커널 개발·설정·서브시스템 문서 |
| `arch/` | CPU 아키텍처별 부팅·인터럽트·메모리·플랫폼 코드 |
| `drivers/` | 장치 및 버스 관련 드라이버 |
| `fs/` | VFS와 파일 시스템 |
| `include/linux/` | 커널 내부에서 널리 공유하는 헤더 |
| `include/uapi/` | 사용자 공간에 공개하는 인터페이스 헤더 |
| `arch/<arch>/include/` | 아키텍처별 헤더 |
| `init/`, `kernel/`, `mm/` | 초기화, 커널 핵심 기능, 메모리 관리 |
| `net/`, `ipc/`, `security/` | 네트워크, 프로세스 간 통신, 보안 |
| `crypto/`, `lib/`, `scripts/` | 암호화, 공통 함수, 빌드 보조 도구 |

1. **Kconfig**는 커널 기능의 선택·의존성을, **Kbuild/Makefile**은 빌드 규칙을 담당한다.
2. 과거 문서의 `configure.help`, 최상위 `include/asm`, `arch/i386` 등은 **현재 소스 트리와 다를 수 있다**. 실제 사용 중인 커널 소스에서 경로를 확인한다.
3. 드라이버를 분석할 때는 관련 `drivers/` 구현과 `include/linux/`, 필요 시 `arch/<arch>/include/`를 함께 찾는다.

```bash
grep -Rnw --include='*.c' --include='*.h' 'readb' drivers/ include/
grep -Rni 'platform_driver' drivers/
```

## 4. 응용 프로그램에서 장치까지

1. 응용 프로그램이 커널 기능을 요청하는 기본 경로는 **시스템 호출(syscall)**이다.
2. `open()`, `read()`, `write()`, `ioctl()`, `close()`로 장치를 다루는 **파일 인터페이스 역시 시스템 호출을 이용**한다. 즉, '시스템 호출 방식'과 '파일 입출력 방식'이 별개인 것은 아니다.
3. 일반적인 문자 장치 흐름:

```text
응용 프로그램
  -> open/read/write/ioctl (시스템 호출)
  -> VFS 및 문자 장치 인터페이스
  -> 드라이버의 file_operations 처리 함수
  -> 하드웨어 또는 커널 자원
```

4. `file_operations`는 드라이버가 제공하는 연산을 커널에 연결한다. 모든 장치가 `read/write/llseek`를 지원하는 것은 아니다.
5. CPU가 커널로 진입하는 명령은 아키텍처에 따라 다르며, 시스템 호출을 단순히 '소프트웨어 인터럽트' 한 가지로만 설명하면 부정확하다.

## 5. 디바이스 파일과 장치 번호

1. `/dev`의 **문자(`c`)·블록(`b`) 장치 노드**는 하드웨어 또는 가상 장치에 접근하는 특수 파일이다. 일반적인 데이터 저장 파일과는 다르다.
2. **주번호(major)**는 관련 커널 장치 처리 경로를 찾는 데 쓰이고, **부번호(minor)**는 해당 드라이버가 관리하는 장치·기능을 구분한다.
3. 장치 노드는 `mknod`로 직접 만들 수 있지만, 실제 시스템에서는 `devtmpfs`와 사용자 공간 장치 관리 도구가 자동으로 생성·관리하는 경우가 많다.
4. 드라이버가 등록되었다고 장치 노드가 반드시 생성되는 것은 아니다. **모듈 적재 여부, 장치 등록, `/dev` 노드 존재를 별개로 점검**한다.
5. 네트워크 장치는 보통 일반적인 `/dev` 장치 노드 대신 네트워크 서브시스템의 인터페이스로 이용한다.

```bash
cat /proc/devices
ls -l /dev/<장치이름>
lsmod
ls /sys/class
```

## 6. 디바이스 드라이버의 기본 분류

| 분류 | 처리 관점 | 예시 |
| --- | --- | --- |
| 문자 장치 | 바이트 스트림 및 장치별 명령 중심 | 시리얼 포트, 간단한 제어 장치 |
| 블록 장치 | 블록 단위 저장장치 I/O 중심 | SSD, SD 카드, 디스크 |
| 네트워크 장치 | 커널 네트워크 스택과 연계 | 이더넷, Wi-Fi 인터페이스 |

1. **문자 장치**도 내부 버퍼나 비동기 처리를 사용할 수 있다. '무조건 버퍼가 없다'는 설명은 부정확하다.
2. **블록 장치**는 파일 시스템을 통해 주로 활용하지만, `/dev`의 블록 장치 자체에 직접 접근하는 것도 가능하다.
3. **네트워크 장치**는 소켓 및 네트워크 스택과 결합하며, 관리는 주로 `ip` 등 네트워크 도구를 사용한다.
4. 현대 커널은 이 기본 분류 외에도 **하드웨어 연결 방식과 기능별 공통 서브시스템**으로 드라이버를 관리한다. 세부 구현은 해당 서브시스템 문서를 따로 학습한다.

## 7. 가상 파일 시스템과 상태 확인

1. `/proc`: 프로세스 및 커널의 실행 상태와 일부 설정을 확인하는 가상 파일 시스템.
2. `/sys`: 커널 장치·드라이버 등 객체의 상태를 확인하는 가상 파일 시스템.
3. `/dev`: 응용 프로그램이 장치 노드를 통해 I/O를 요청하는 주요 위치.
4. **세 경로는 역할이 다르며**, 드라이버 구현에 따라 모든 인터페이스가 필요한 것은 아니다.

## 8. 과거 설명에서 주의할 부분

1. 커널 모듈 문제는 **단순한 버전 번호 불일치**가 아니라 빌드·API·심볼 호환성 문제로 이해한다.
2. 시스템 호출과 파일 I/O는 경쟁 관계가 아니다. **파일 I/O가 시스템 호출 위에서 동작**한다.
3. 문자 장치의 버퍼·파일 위치 지원 여부는 드라이버별로 다르다.
4. 오래된 아키텍처 목록과 헤더 위치를 그대로 암기하지 말고 **현재 사용하는 커널 소스**를 기준으로 확인한다.
5. 책의 오래된 장치 관리 표현보다는 **최신 공식 커널 문서와 실제 소스**를 우선한다.

## 9. 학습 우선순위

1. 우선 학습: **시스템 호출 → `file_operations` → 주/부번호 → 문자 드라이버의 등록·제거 → 사용자 프로그램 연결**.
2. 실습 확인: `insmod`, `lsmod`, `dmesg`, `/proc/devices`, `/dev`를 통해 실패 지점을 분리한다.
3. 후순위: 전체 커널 계층·버스별 구현 세부 사항. 실제로 사용하는 드라이버를 만날 때 확장한다.
