# 리눅스 커널 드라이버: 장치 식별, 제어, 타이머, 인터럽트

- 학습일: 2026-11-17 (KST)
- 학습 범위: 디바이스 드라이버 교재 PDF 254~382쪽
- 학습 환경 참고: Raspberry Pi 5, Linux 커널 6.12 계열
- 주의: 교재의 예제는 주로 Linux 2.4/2.6 기준이다. 원리는 학습하되 API는 현재 커널에 맞게 확인한다.

## 1. 주 번호와 부 번호 (254~292쪽)

### 1.1 개념

1. **주 번호(Major)**: 디바이스 파일을 어떤 드라이버가 처리할지 식별한다.
2. **부 번호(Minor)**: 같은 드라이버가 담당하는 여러 장치 또는 기능을 구분한다.
3. **`dev_t`**: 주 번호와 부 번호를 함께 표현하는 타입이다.
4. **`MKDEV(major, minor)`**, **`MAJOR(dev)`**, **`MINOR(dev)`**로 번호를 결합하거나 추출한다. `inode`에서는 `imajor(inode)`, `iminor(inode)`를 사용할 수 있다.

```text
/dev/led0  -> Major 237, Minor 0 -> LED 0
/dev/led1  -> Major 237, Minor 1 -> LED 1
/dev/led2  -> Major 237, Minor 2 -> LED 2
```

위 번호는 설명용이다. 실제 디바이스 노드는 커널에 등록된 주·부 번호와 일치해야 한다.

### 1.2 부 번호로 장치를 구분하는 예제

```c
static int led_open(struct inode *inode, struct file *filp)
{
    unsigned int minor = iminor(inode);

    if (minor >= LED_COUNT)
        return -ENODEV;

    filp->private_data = &leds[minor];
    return 0;
}
```

1. 프로그램이 `/dev/led1`을 `open()`한다.
2. 커널이 등록된 드라이버의 `.open`을 호출한다.
3. `iminor(inode)`가 부 번호 `1`을 제공한다.
4. `filp->private_data`에 `leds[1]`의 주소를 저장한다.
5. 이후 `.read`나 `.write`에서 해당 주소로 장치별 데이터를 접근한다.

교재의 예제는 부 번호에 따라 `file_operations`를 전환해 읽기용과 쓰기용 기능을 구분한다. 현재 실습에서는 하나의 `file_operations`와 장치별 `private_data`를 사용하는 구조가 이해하기 쉽다. `filp->f_op`를 임의로 직접 바꾸는 코드를 그대로 사용하지 않는다.

### 1.3 주 번호 등록

- 고정된 주 번호를 임의로 가정하기보다 `alloc_chrdev_region()`으로 동적으로 할당하는 방식이 일반적이다.
- `cdev_init()`과 `cdev_add()`로 문자 디바이스 처리를 등록할 수 있다.
- `/proc/devices`, `ls -l /dev/장치명`으로 등록 정보를 확인한다.

## 2. ioctl을 이용한 디바이스 제어 (293~318쪽)

### 2.1 역할

1. `read()`: 데이터 읽기
2. `write()`: 데이터 쓰기
3. `ioctl()`: 읽기·쓰기만으로 표현하기 어려운 장치 설정, 상태 조회, 제어 명령 전달

### 2.2 명령 매크로

| 매크로 | 의미 |
| --- | --- |
| `_IO(type, nr)` | 추가 데이터 없이 명령 전달 |
| `_IOR(type, nr, data_type)` | 커널에서 사용자 공간으로 데이터 전달 |
| `_IOW(type, nr, data_type)` | 사용자 공간에서 커널로 데이터 전달 |
| `_IOWR(type, nr, data_type)` | 양방향 데이터 교환 |

읽기·쓰기 방향은 사용자 프로그램 기준이다. 명령에는 일반적으로 방향, 데이터 크기, 타입(매직 번호), 명령 번호가 포함된다.

```c
#define LED_MAGIC 'L'
#define LED_ON    _IO(LED_MAGIC, 0)
#define LED_SET   _IOW(LED_MAGIC, 1, int)
#define LED_GET   _IOR(LED_MAGIC, 2, int)
```

- 사용자 프로그램: `ioctl(fd, LED_SET, &value)`
- 커널 드라이버: `file_operations.unlocked_ioctl` 콜백에서 `cmd`를 분기한다.
- 사용자 공간 포인터는 직접 역참조하지 않고 `copy_from_user()` 또는 `copy_to_user()`로 접근한다.
- 알 수 없는 명령에는 일반적으로 `-ENOTTY`를 반환한다.

## 3. 시간 처리와 커널 타이머 (319~342쪽)

### 3.1 시간의 기준

1. **`HZ`**: 커널의 초당 틱 수를 나타내는 설정값이다.
2. **`jiffies`**: 커널 틱을 기준으로 증가하는 카운터다.
3. **`msecs_to_jiffies()`**: 밀리초를 jiffies 값으로 변환한다.
4. 상대 시간 계산에는 `jiffies + msecs_to_jiffies(300)`과 같은 형태를 사용할 수 있다.

### 3.2 지연 함수

- `udelay()`, `mdelay()`: CPU를 점유하는 Busy Wait. 매우 짧은 하드웨어 타이밍에 한정한다.
- `msleep()`, `usleep_range()` 등: 슬립 가능한 프로세스 문맥에서 CPU를 양보하며 기다린다.
- 하드 IRQ 핸들러나 일반 타이머 콜백에서는 잠드는 함수를 호출하면 안 된다.

### 3.3 커널 2.6의 선점형(Preemptive) 의미

1. **선점**은 실행 중인 작업이 자발적으로 CPU를 양보하지 않아도, 커널이 선점 가능한 시점에 다른 태스크를 실행할 수 있다는 뜻이다.
2. 교재의 커널 2.4 예제는 `while (...) schedule();`로 명시적으로 스케줄러를 호출한다.
3. 커널 2.6 예제는 선점형 커널에서 `while (...);` 중에도 태스크 전환이 일어날 수 있다고 설명한다.
4. 그러나 **모든 2.6 커널이 선점형으로 설정된 것은 아니다.** 선점 가능 여부는 커널 설정과 실행 문맥에 따라 달라진다.
5. 또한 `while (...);`는 여전히 CPU를 소비하는 Busy Wait이므로 긴 지연에 적합하지 않다.

### 3.4 현대 커널 타이머의 흐름

```text
timer_setup()  ->  mod_timer()  ->  타이머 만료/콜백 실행
                                     |
                                     +-- 반복 시 mod_timer() 재등록
```

- `timer_setup()`: 타이머와 콜백 연결
- `mod_timer()`: 만료 시점 예약 또는 변경
- `timer_shutdown_sync()`: 종료 시 재등록을 막고 실행 중인 콜백과 동기화
- 타이머 콜백은 일반적으로 소프트 IRQ 문맥에서 실행되므로 슬립하면 안 된다.

## 4. 인터럽트 처리 (343~381쪽)

### 4.1 처리 순서

```text
GPIO 입력 변화 -> IRQ 발생 -> 커널의 IRQ 처리 -> 등록된 ISR 호출
                                                  |
                                      이벤트 상태 기록 / 대기자 깨우기
                                                  |
                                           기존 실행 흐름 복귀
```

1. 하드웨어 이벤트로 IRQ가 발생한다.
2. 커널은 등록된 인터럽트 핸들러를 실행한다.
3. 핸들러는 필요한 최소 작업을 수행하고 `IRQ_HANDLED` 또는 `IRQ_NONE`을 반환한다.
4. 시간이 오래 걸리는 작업이나 슬립이 필요한 처리는 threaded IRQ 또는 workqueue 등으로 분리한다.

### 4.2 주요 함수 및 인자

- `request_irq()`: IRQ 핸들러 등록
- `free_irq()`: 등록한 IRQ 핸들러 해제
- `devm_request_irq()`: 장치 관리 방식으로 IRQ 등록
- `gpiod_to_irq()`: GPIO 디스크립터에서 IRQ 번호 획득
- `dev_id`: 등록 시 전달한 장치별 데이터 포인터이며 ISR에서도 동일하게 전달된다.
- `IRQF_TRIGGER_RISING` / `IRQF_TRIGGER_FALLING`: 상승/하강 에지 요청

```c
static irqreturn_t key_isr(int irq, void *dev_id)
{
    struct key_dev *dev = dev_id;

    atomic_inc(&dev->events);
    wake_up_interruptible(&dev->waitq);
    return IRQ_HANDLED;
}
```

### 4.3 동시성과 주의점

1. ISR과 일반 드라이버 코드가 데이터를 공유하면 동기화를 고려해야 한다.
2. 단순 이벤트 카운터는 `atomic_t`를 활용할 수 있다.
3. 복수 필드를 함께 갱신하면 Spinlock 등 적절한 동기화 도구를 사용한다.
4. 하드 IRQ 문맥에서는 `mutex_lock()`, `msleep()`, `GFP_KERNEL` 할당처럼 잠들 수 있는 작업을 하면 안 된다.
5. `dev_id`와 `private_data`에 장치별 구조체를 연결하면 전역 변수 의존도를 줄일 수 있다.
6. IRQ 등록 해제 전에 장치의 인터럽트 발생과 자원 수명을 정리해야 한다.

### 4.4 실습 확인 명령

```bash
cat /proc/interrupts
cat /proc/devices
ls -l /dev/multi_led_key
dmesg -w
```

## 5. 복습 핵심

1. **Major/Minor**: 커널이 드라이버를 찾고, 드라이버가 내부 장치 또는 기능을 구분하는 방법
2. **`private_data`**: `open()`에서 찾은 장치 정보를 이후 파일 작업에 전달하는 방법
3. **`ioctl()`**: 장치에 별도 제어 명령을 전달하고 사용자/커널 공간 데이터를 교환하는 방법
4. **커널 선점**: 커널 실행 도중에도 조건이 맞으면 다른 태스크로 CPU가 전환될 수 있다는 뜻. Busy Wait의 정당화는 아님
5. **타이머**: 미래 시점의 콜백을 예약하는 장치. 주기적 작업은 재예약 필요
6. **IRQ**: 하드웨어 이벤트를 받아 최소 처리 후 안전하게 후속 작업으로 넘기는 방법

## 6. 현대 커널로 옮길 때 주의할 구형 API

| 교재 기준 표현 | Linux 6.12 학습 방향 |
| --- | --- |
| 구형 `.ioctl` 콜백 | `.unlocked_ioctl` |
| `verify_area()` | `copy_to_user()`, `copy_from_user()` 등 |
| `init_timer()` 및 구형 콜백 | `timer_setup()` |
| 타이머 종료 시 `del_timer()`에만 의존 | 콜백의 재등록 여부와 동기화 확인, `timer_shutdown_sync()` 고려 |
| `SA_INTERRUPT`, `SA_SHIRQ` | 현재의 `IRQF_*` 플래그 |
| 고정 주 번호 전제 | 동적 할당 및 등록 번호 확인 |
