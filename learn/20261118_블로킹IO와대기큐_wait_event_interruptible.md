# 리눅스 블로킹 I/O와 대기 큐: wait_event_interruptible, 인터럽트 깨움과 타임아웃

장치의 데이터나 전송 공간이 준비될 때까지 호출 태스크를 재우는 블로킹 I/O를 공부했다. 응용 프로그램의 파일 플래그, 드라이버가 유지하는 준비 조건, 대기 큐와 인터럽트의 역할을 연결하고, 조건 검사와 잠들기 사이에서 깨움을 놓치지 않는 `wait_event_interruptible()`의 동작을 정리했다. 인터럽트 시각을 기록하는 장치를 새 사례로 구성해 반환 크기, 시그널, 시간 제한, 기록 버퍼의 의미까지 살펴봤다.

## 1. 블로킹 여부는 파일 플래그와 드라이버 구현이 함께 결정한다

블로킹 I/O는 입출력을 진행할 조건이 없을 때 호출 태스크가 기다리도록 하는 처리다. 읽기는 수신 데이터, 쓰기는 송신 공간이나 장치의 완료 상태를 기다릴 수 있다. 시스템 호출이 진행되는 동안 응용 프로그램의 해당 스레드는 다음 명령으로 넘어가지 못하지만, CPU는 다른 실행 가능한 태스크를 처리할 수 있다. 이미 조건이 충족되어 있다면 블로킹 모드로 열었어도 대기하지 않는다.

`open()`의 `O_RDONLY`, `O_WRONLY`, `O_RDWR`은 접근 방향을 정한다. `O_NONBLOCK`을 더하면 지원하는 장치에서 입출력 준비를 기다리지 않는 모드가 된다. 리눅스의 `O_NDELAY`는 같은 플래그의 다른 이름이며, 새 코드에서는 `O_NONBLOCK`으로 표현한다. 드라이버는 `filp->f_flags & O_NONBLOCK`으로 현재 모드를 확인한다. 플래그를 생략했다고 커널이 모든 장치의 `.read`와 `.write`를 자동으로 재우는 것은 아니다. 실제 대기와 비블로킹 분기는 드라이버의 구현에 달려 있다. [`open(2)`](https://man7.org/linux/man-pages/man2/open.2.html)

| 장치의 준비 상태 | 블로킹 모드 | 비블로킹 모드 |
| --- | --- | --- |
| 지금 처리할 데이터나 공간이 있다 | 가능한 분량을 처리한다. | 가능한 분량을 처리한다. |
| 지금 처리할 수 있는 분량이 없다 | 준비 조건을 기다린다. | 일반적인 스트림 장치는 `-EAGAIN`을 반환한다. |
| 현재 상태를 즉시 읽거나 쓰는 장치다 | 대기 없이 끝날 수 있다. | 장치가 같은 동작을 제공할 수 있다. |

`read()`의 양수 반환값은 실제 전달한 **바이트 수**다. 블로킹이라는 이유만으로 요청한 길이를 항상 전부 채워야 하는 것은 아니다. 예를 들어 40바이트를 요청하고 16바이트를 받는 짧은 읽기도 성공일 수 있다. 직렬 포트의 구체적인 완료 조건은 터미널 설정 등에도 영향을 받는다. 커널 콜백의 `-EAGAIN`은 일반적인 사용자 공간 호출에서 `-1`과 `errno == EAGAIN`으로 보인다. 데이터가 아직 없는 상태를 무조건 읽기 결과 `0`으로 표시하면 입력 종료를 뜻하는 EOF와 혼동하기 쉽다. [`read(2)`](https://man7.org/linux/man-pages/man2/read.2.html)

터미널의 비정규 모드에는 `VMIN`·`VTIME` 설정에 따라 데이터 없이 `0`을 반환하는 경우가 있다. POSIX도 비블로킹 비정규 읽기에서 데이터가 없을 때 `0` 또는 `EAGAIN`을 허용하므로, 이 장치 종류의 규칙을 일반 문자 스트림의 반환 규약과 구별한다. [`termios(3)`](https://man7.org/linux/man-pages/man3/termios.3.html)

## 2. 이벤트를 기다리는 태스크는 CPU를 계속 사용할 필요가 없다

한 논리 CPU에서는 태스크들이 번갈아 실행되며, 여러 CPU가 있으면 병렬 실행도 가능하다. 계산할 수 있는 태스크가 많을수록 CPU 시간을 나누어 쓰지만, 입력을 기다리며 잠든 태스크는 일반적인 실행 경쟁에서 빠진다. 장시간 유지되는 데몬도 할 일이 없을 때 대기하면 CPU를 계속 소비하지 않는다. `ps`와 `top`으로 태스크의 상태와 CPU 사용량을 함께 관찰할 수 있다.

**CPU를 선점당해 실행을 기다리는 상태와 이벤트가 없어 잠든 상태는 다르다.** 전자는 계속 실행 가능한 태스크이고, 후자는 준비 조건이나 시그널 등으로 깨어나야 실행 후보가 된다. 잠들기는 프로세스 종료와도 다르므로, 재개되면 기존 커널 호출의 진행 지점에서 이어진다. CPU가 장치보다 빠르게 상태를 검사할 수 있어도, 이벤트가 없는 동안 반복 검사하면 그 시간을 다른 작업에 사용할 기회를 잃는다.

틱 주파수 `HZ`를 모든 태스크의 고정 실행 시간으로 해석하면 안 된다. 스케줄링 정책, 우선순위, 실행 가능한 태스크 수와 선점 설정 등이 실제 실행 순서에 영향을 준다. 현행 일반 태스크의 공정 스케줄링은 EEVDF를 사용하며, 커널 세대만 보고 각 태스크가 일정한 밀리초 간격으로 실행된다고 계산할 수 없다. CPU 클럭 역시 명령 처리량과 일대일로 같지 않다. [EEVDF 스케줄러](https://docs.kernel.org/scheduler/sched-eevdf.html)

응용 프로그램에서 기다리는 방법도 목적에 따라 구별한다.

- `sleep()`은 요청한 시간의 경과나 시그널을 기다린다. 장치 이벤트가 생겼다는 사실을 직접 전달받는 방법은 아니다.
- `select()`와 `poll()`은 여러 파일 디스크립터의 입출력 준비를 함께 기다릴 수 있다. 드라이버가 적절한 준비 상태와 대기 등록을 제공해야 한다. 비블로킹 읽기를 끊임없이 재시도하는 루프의 CPU 낭비를 줄일 수 있다. [`poll(2)`](https://man7.org/linux/man-pages/man2/poll.2.html)
- `sched_yield()`는 CPU를 자발적으로 양보하는 호출이다. 특정 장치 조건이 생길 때까지 잠드는 대기 장치를 만들지는 않으며, 다른 실행 후보가 없으면 곧바로 다시 실행될 수도 있다. [`sched_yield(2)`](https://man7.org/linux/man-pages/man2/sched_yield.2.html)

## 3. 대기 큐는 준비 조건을 기다리는 태스크들을 연결한다

대기 큐는 같은 조건을 기다리는 태스크들을 관리하는 커널 자료구조다. 하나의 장치를 여러 프로세스가 열어 같은 읽기 조건을 기다릴 수 있고, 한 드라이버 안에서도 읽기 데이터와 쓰기 공간처럼 다른 조건이 존재할 수 있다. 읽기용과 쓰기용 큐를 나누면 변화한 조건에 맞는 대기자들을 깨울 수 있다. 반드시 연산마다 별도 큐를 만들어야 하는 것은 아니며, 조건과 깨움 범위를 보고 설계한다.

현행 선언과 초기화에는 `<linux/wait.h>`를 사용한다.

| 인터페이스 | 역할과 인자 |
| --- | --- |
| `wait_queue_head_t` | 대기 큐의 헤드를 표현한다. 내부에 큐 관리용 락과 목록이 있다. |
| `init_waitqueue_head(&dev->read_wait)` | 이미 확보한 장치 상태 안의 큐를 초기화한다. |
| `DECLARE_WAIT_QUEUE_HEAD(status_wait)` | 큐 변수를 선언하면서 초기화한다. |
| `wait_event_interruptible(dev->read_wait, 조건식)` | 큐 객체와 준비 조건을 받아 대기한다. |
| `wake_up_interruptible(&dev->read_wait)` | 큐의 주소를 받아 interruptible 대기자들을 깨운다. |

큐는 대기자나 IRQ 핸들러가 접근하기 전에 초기화한다. 여러 콜백이 함께 참조해야 한다는 이유로 반드시 전역 변수일 필요는 없다. 장치별 상태에 두고 열린 파일의 `private_data`나 IRQ의 `dev_id`로 찾아도 된다. [현행 대기 큐 선언과 매크로](https://github.com/torvalds/linux/blob/master/include/linux/wait.h)

**대기 큐와 이벤트 데이터는 별개다.** 큐가 비어 있어도 깨움 호출은 가능하지만, 깨움 자체를 다음 대기자를 위한 이벤트로 보관하지는 않는다. 데이터, 개수, 준비 플래그 같은 상태를 별도로 남겨야 나중에 들어온 읽기도 조건을 확인할 수 있다. 생산자는 먼저 데이터를 기록하고 준비 상태를 바꾼 뒤 해당 큐를 깨운다. 깨움은 태스크를 실행 가능한 상태로 전환하는 동작이며, 그 태스크의 사용자 코드가 즉시 실행된다는 보장은 없다. 스케줄러가 CPU를 배정하면 대기하던 커널 코드부터 재개된다. [대기 등록과 깨움 구현](https://github.com/torvalds/linux/blob/master/kernel/sched/wait.c)

일반적인 비배타적 대기자가 여러 명이면 함께 깨어날 수 있다. 배타적 대기 항목을 사용하면 깨우는 수가 달라지므로, `wake_up_interruptible()`을 언제나 모든 태스크를 실행시키는 함수로 이해하면 안 된다. 여러 독자가 한 데이터를 경쟁해서 가져가는 장치라면 깨운 뒤에도 각 독자가 준비 상태와 데이터 소유권을 다시 확인해야 한다. [깨움 대상 선택](https://github.com/torvalds/linux/blob/master/kernel/sched/wait.c)

## 4. 조건 검사와 잠들기를 wait_event 계열로 연결한다

### 4.1 깨움을 놓치는 경쟁을 피한다

데이터가 없음을 확인한 뒤 별도의 호출로 잠들기만 하면 다음 순서가 가능하다.

1. 읽기 콜백이 버퍼가 비었다고 확인한다.
2. 읽기 태스크가 아직 대기 큐에 들어가기 전에 인터럽트가 데이터를 저장하고 깨움을 호출한다.
3. 읽기 태스크가 그 뒤에 잠들면 이미 있는 데이터를 처리하지 못한 채 다음 깨움을 기다릴 수 있다.

구형 `interruptible_sleep_on()`과 `interruptible_sleep_on_timeout()`은 이런 경쟁 문제가 있던 인터페이스다. 과거 커널 헤더도 사용하지 말고 `wait_event*`로 전환하라고 명시했으며, 현행 헤더에는 이 함수들이 없다. 조건 없는 잠들기를 옮겨 적는 대신, 준비 조건을 함께 전달하는 `wait_event_interruptible()`과 시간 제한 변형을 사용한다. [과거 인터페이스의 폐기 안내](https://github.com/torvalds/linux/blob/v3.13/include/linux/wait.h), [현행 헤더](https://github.com/torvalds/linux/blob/master/include/linux/wait.h)

### 4.2 깨어났다는 사실과 조건의 성립을 구별한다

`wait_event_interruptible()`은 조건이 이미 참이면 잠들지 않고 성공한다. 거짓이면 대기 등록과 조건 재확인을 연결하고, `TASK_INTERRUPTIBLE` 상태로 기다린다. 깨운 뒤에도 조건이 거짓이면 다시 기다릴 수 있다. 조건식은 반복 평가되므로 부작용 없이 준비 상태를 검사하도록 작성한다. 예를 들어 기록을 네 개 모으는 조건은 `record_count >= 4`로 표현할 수 있으며, 개수가 둘일 때 큐를 깨웠다는 사실만으로 대기가 성공하지 않는다.

조건을 만족해 끝나면 `0`, 시그널로 중단되면 `-ERESTARTSYS`를 반환한다. 읽기 콜백은 아직 아무 데이터도 전달하지 않았다면 이 음수 결과를 상위로 돌려주어야 한다. 사용자 공간에서는 시그널 처리 설정에 따라 시스템 호출이 재시작되거나 `EINTR`로 관찰될 수 있다. 하드 IRQ 핸들러는 준비 상태를 갱신하고 깨움을 호출하는 쪽이며, 이처럼 잠들 수 있는 대기 호출은 슬립 가능한 프로세스 문맥에서 수행한다. [대기와 시그널의 반환 규칙](https://docs.kernel.org/driver-api/basics.html#c.wait_event_interruptible), [`read(2)`](https://man7.org/linux/man-pages/man2/read.2.html)

비블로킹 읽기는 준비된 데이터가 없을 때 대기 매크로로 들어가지 않고 `-EAGAIN`을 반환하도록 분기한다. 여러 독자가 데이터를 소비하는 구조에서는 깨어난 뒤 다른 독자가 먼저 가져갈 수 있으므로, 데이터 확보가 실패하면 현재 모드에 따라 다시 기다리거나 `-EAGAIN`으로 끝낸다.

### 4.3 대기 큐의 락은 데이터 버퍼까지 보호하지 않는다

IRQ 핸들러의 데이터 추가, 읽기의 상태 확인, 기록 초기화는 같은 상태에 접근한다. 대기 큐가 내부 목록을 보호해도 드라이버 버퍼와 카운터까지 자동으로 동기화하지는 않는다. 일반적인 비실시간 커널에서 하드 IRQ와 프로세스 문맥이 상태를 공유하면, 프로세스 쪽에서는 `spin_lock_irqsave()` 계열을 사용해 같은 CPU의 IRQ와 다른 CPU 접근을 함께 고려할 수 있다. 스핀락을 잡은 채 일반 대기 매크로를 호출해 잠들어서는 안 된다. [스핀락과 IRQ 사이의 동기화](https://docs.kernel.org/locking/spinlocks.html)

조건 검사까지 락으로 묶어야 한다면 락을 놓고 잠들었다가 다시 잡도록 설계된 `wait_event_interruptible_lock_irq()` 같은 변형도 있다. 일반 매크로를 사용할 때도 조건 관찰과 데이터 접근의 락·원자성 규칙을 설계해야 한다. `READ_ONCE()` 하나를 붙이는 것만으로 버퍼 전체와 복합 상태의 동기화가 끝나지는 않는다. [락을 사용하는 대기 변형](https://github.com/torvalds/linux/blob/master/include/linux/wait.h)

## 5. 시간 제한은 jiffies 단위와 반환값을 함께 해석한다

이벤트가 오지 않을 때 무기한 대기하지 않으려면 `wait_event_interruptible_timeout(큐, 조건식, 제한시간)`을 사용한다. 마지막 인자는 `HZ` 자체가 아니라 **jiffies 단위의 대기 길이**다. `HZ`는 초당 틱 수이므로, 밀리초로 정한 정책은 `msecs_to_jiffies()`로 변환해 전달한다. 커널 버전만 보고 한 틱이 항상 같은 시간이라고 가정하지 않는다. [jiffies와 시간 변환 구현](https://github.com/torvalds/linux/blob/master/include/linux/jiffies.h)

| 반환값 | 의미 | 호출자가 할 일 |
| --- | --- | --- |
| `> 0` | 조건이 성립했다. 일찍 끝나면 남은 jiffies이며 최소 1이다. 만료 경계에서 조건이 참이어도 1을 반환한다. | 데이터를 안전하게 확보하고 처리한다. |
| `0` | 제한시간이 지났는데 조건이 거짓이다. | 장치 인터페이스가 정한 타임아웃 결과를 반환한다. |
| `-ERESTARTSYS` | 시그널로 대기를 중단했다. | 아직 처리한 데이터가 없다면 오류를 상위로 전달한다. |

양수 결과는 경과한 시간이 아니다. 예를 들어 제한시간이 90틱이고 28을 반환했다면 약 62틱을 기다린 것으로 계산할 수 있다. 이 계산과 별개로 실제 태스크가 다시 실행되는 데에는 스케줄링 지연이 더해질 수 있다. 대기 매크로의 `0`을 곧바로 읽기 결과 `0`으로 반환할지도 별도로 정해야 한다. 읽기 인터페이스에서 EOF를 뜻하게 될 수 있기 때문이다. [타임아웃 대기 반환 규칙](https://docs.kernel.org/driver-api/basics.html#c.wait_event_interruptible_timeout)

## 6. 인터럽트 시각 기록 장치로 전체 흐름을 구성한다

### 6.1 기록과 읽기의 의미를 먼저 정한다

새 사례로, 입력 접점의 변화 시각을 최대 48개까지 모으고 출력 표시등을 제어하는 장치를 생각했다. 각 기록은 부팅 후 단조 시간의 나노초 값 하나를 담는다. 기록을 읽는 동작은 현재 누적 내용을 복사하는 **스냅샷 조회**로 정하고, 측정 시작 명령이 버퍼와 개수를 초기화하도록 한다. 읽기 자체로 기록을 제거하지 않으므로 첫 이벤트 이후의 다음 읽기는 새 이벤트가 없어도 바로 성공할 수 있다. 매번 새로운 이벤트를 기다리려면 소비하는 큐, 순번, 열린 파일별 읽기 위치 같은 별도 규약이 필요하다.

시간을 틱으로 관찰하는 목적이라면 현재도 `jiffies`나 `get_jiffies_64()`를 사용할 수 있다. 다만 여러 이벤트가 같은 틱 안에 발생하면 타임스탬프가 같을 수 있어 미세한 간격을 구별하기 어렵다. 새 사례처럼 간격 측정이 목적이면 `ktime_get_ns()`로 단조 시간의 나노초 값을 얻는다. 나노초 단위로 표현된다는 것이 실제 하드웨어 정밀도나 인터럽트 응답 지연까지 나노초로 보장한다는 뜻은 아니다. [틱 카운터](https://github.com/torvalds/linux/blob/master/include/linux/jiffies.h), [커널 시간 조회](https://docs.kernel.org/core-api/timekeeping.html)

사용자 공간에 내보내는 레코드는 아키텍처에 따라 폭이 달라지는 `unsigned long` 대신 `__u64` 같은 고정 폭 필드를 사용한다. 이 사례에서는 레코드 하나가 8바이트다. 여러 필드가 있으면 정렬과 패딩도 정해야 하며, `packed` 지정만으로 32·64비트 호환 문제가 모두 해결되지는 않는다. [사용자 인터페이스의 구조체 배치 원칙](https://docs.kernel.org/driver-api/ioctl.html#structure-layout)

### 6.2 준비, 이벤트 생산, 대기 해제를 연결한다

1. 드라이버가 장치 상태, 버퍼, 락, 대기 큐를 초기화하고 IRQ 처리에 필요한 자원을 준비한다. `request_irq()`는 성공 시 0, 실패 시 오류를 반환하므로 실패를 호출자에게 전달한다. 등록 시점부터 핸들러가 호출될 수 있으므로 버퍼 초기화를 그 뒤로 미루지 않는다.
2. 읽기 콜백은 기록 유무와 `O_NONBLOCK`을 확인한다. 기록이 없고 블로킹 모드이면 준비 조건이 참이 될 때까지 기다린다.
3. IRQ 핸들러는 자기 장치의 이벤트인지 확인하고 필요한 장치 측 처리를 한다. 공간이 있으면 시각과 개수를 동기화해 갱신하고, 가득 찼다면 정해 둔 초과 정책을 적용한다. 그 뒤 읽기 대기 큐를 깨운다.
4. 읽기 태스크가 실행 기회를 얻으면 대기 결과를 검사하고, 일관된 기록 복사본을 사용자 공간에 전달한다.
5. 마지막 사용 종료나 장치 제거에서는 새 이벤트 발생을 막고 실행 중인 IRQ 처리와 동기화한 뒤 자원을 해제한다. IRQ 등록과 해제를 `.open`·`.release`에 두는 설계는 여러 열기의 소유권과 첫 열기·마지막 닫기를 관리해야 한다. 장치 수명 동안 한 번 등록하는 설계도 가능하다.

현행 일반 IRQ 핸들러 형식은 `irqreturn_t handler(int irq, void *dev_id)`이며, 과거의 `struct pt_regs *` 인자를 전달받지 않는다. 자기 장치의 이벤트를 처리했으면 `IRQ_HANDLED`, 공유 IRQ에서 자기 장치의 원인이 아니면 `IRQ_NONE`을 반환한다. `SA_INTERRUPT`도 현행 요청 플래그가 아니므로 그대로 옮기지 않는다. 공유 여부와 트리거 설정 등 실제 장치에 필요한 플래그를 선택하고, 공유 IRQ라면 장치별 `dev_id`와 원인 확인을 사용한다. [현행 IRQ 인터페이스](https://github.com/torvalds/linux/blob/master/include/linux/interrupt.h), [IRQ 등록과 해제](https://docs.kernel.org/core-api/genericirq.html)

이 사례에서 저장 개수는 버퍼가 가득 차면 48에서 더 증가시키지 않는 것으로 정할 수 있다. 그러면 저장 개수는 전체 IRQ 발생 횟수와 같지 않으므로, 버려진 이벤트까지 알고 싶다면 별도 초과 카운터가 필요하다. 용량 확인과 기록·개수 갱신은 같은 동기화 규칙으로 묶는다.

### 6.3 요청 크기는 레코드 수로 계산하고 반환은 바이트로 한다

읽기가 전달할 레코드 수는 `요청 바이트 수 / 레코드 크기`와 현재 저장 개수 중 작은 값이다. 위 사례에서 8바이트 레코드가 7개 있고 앱이 26바이트를 요청하면 완전한 레코드 3개, 총 24바이트를 전달할 수 있다. 응용 프로그램은 읽기 반환값을 먼저 검사한 뒤 레코드 크기로 나누어 출력할 개수를 얻는다. 음수 오류를 레코드 수로 해석해서는 안 된다. [`read(2)`](https://man7.org/linux/man-pages/man2/read.2.html)

길이 0인 정상 읽기는 대기 없이 0으로 끝낸다. 0보다 크지만 레코드 하나보다 작은 요청은 이 장치의 규약상 `-EINVAL`로 처리하도록 정할 수 있다. IRQ와 공유하는 버퍼는 짧은 락 구간에서 임시 커널 버퍼로 복사하고, 락을 놓은 뒤 사용자 복사를 수행한다. `copy_to_user()`·`copy_from_user()`는 복사하지 못한 바이트 수, `put_user()`·`get_user()`는 성공 시 0 또는 실패 시 오류를 반환하므로 결과를 확인한다. 복사 실패를 무시하고 요청한 크기를 전부 성공했다고 반환하면 안 된다. [사용자 복사 규칙](https://github.com/torvalds/linux/blob/master/include/linux/uaccess.h)

쓰기 명령도 먼저 사용자 데이터를 가져와 검증한 뒤 적용한다. 여러 입력 바이트를 처리하는 인터페이스라면 입력 포인터를 전진시켜야 하며, 모든 반복에서 첫 바이트만 다시 읽지 않는다. 기록 초기화와 출력 변경이 하나의 명령이라면 두 동작의 동기화 범위를 정의한다. 측정 중 표시등을 바꿀 때 기록을 유지하려면 초기화 명령과 출력 명령을 구분하는 편이 명확하다.

### 6.4 대기와 누적 관측을 구별해 시험한다

응용 프로그램은 측정을 시작하며 표시등을 켜고, 첫 기록을 읽어 이벤트 도착을 기다린다. 첫 읽기가 성공하면 약 500ms의 관측 구간을 더 둔 뒤 누적 기록을 조회한다. 이어 표시등을 300ms 간격으로 세 차례 점멸하고 장치를 닫는 흐름으로 구성할 수 있다. 이때 첫 읽기는 이벤트 대기이고 이후의 시간 지연은 관측 구간이나 표시 동작을 위한 것으로, 목적이 다르다.

기계 접점은 한 번 조작해도 채터링으로 여러 입력 변화를 만들 수 있다. 기록 수가 여러 개라는 사실만으로 드라이버가 같은 이벤트를 중복 저장했다고 판단하지 않는다. 기록 시각의 간격을 확인하고, 틱 단위로 기록했다면 같은 값 안에 여러 IRQ가 들어갈 수 있음도 고려한다. 모든 에지를 기록하는 측정 장치와 한 번의 누름만 전달하는 입력 장치는 필요한 디바운스 정책이 다르다.

## 7. 빌드와 장치 공개는 실행 환경의 자원에 맞춘다

현재 외부 커널 모듈은 실행할 커널의 설정·헤더·빌드 결과를 사용해 Kbuild로 빌드하고 `.ko`를 적재한다. 모듈 등록·해제에는 `module_init()`과 `module_exit()`를 사용한다. 사용자 프로그램은 일반 C 컴파일러로 별도 빌드하며, 모듈은 의존성을 준비한 뒤 `insmod`, 등록 확인은 `lsmod`, 사용 종료 후 해제는 `rmmod`로 수행할 수 있다. [외부 모듈 빌드](https://docs.kernel.org/kbuild/modules.html)

문자 장치의 `file_operations`에는 `.open`, `.read`, `.write`, `.release` 등 필요한 콜백을 연결하고 `.owner`를 `THIS_MODULE`로 지정한다. 파일 연산을 사용하는 동안 모듈 참조를 유지하는 경로와, 각 콜백에서 장치 자원을 관리하는 수명을 함께 고려한다. [문자 장치 열기와 파일 연산 참조](https://github.com/torvalds/linux/blob/master/fs/char_dev.c)

문자 장치 번호는 `alloc_chrdev_region()`과 `cdev_add()`로 동적 할당·등록하거나, 단일 노드 장치는 `misc_register()`와 `MISC_DYNAMIC_MINOR`를 사용할 수 있다. `register_chrdev()`도 현재 남아 있지만 임의의 고정 주 번호가 비어 있다고 가정하지 않는다. 수동 `mknod`는 노드의 종류와 주·부 번호를 기록하는 동작이며 드라이버를 등록하지 않는다. 수동 노드는 모듈 적재 전후 어느 때 만들더라도 실제 `open()` 시점에는 번호와 드라이버 등록이 맞아야 한다. 장치를 커널 디바이스 모델에 등록하면 devtmpfs 등의 구성으로 노드 생성을 연결할 수도 있다. [문자 장치 등록 소스](https://github.com/torvalds/linux/blob/master/fs/char_dev.c), [misc 장치 등록](https://docs.kernel.org/driver-api/misc_devices.html)

병렬 포트가 실제 있는 환경에서는 데이터 출력선, 인터럽트 입력선, 신호 기준이 되는 접지를 구별해 연결해야 한다. 포트 주소와 IRQ를 특정 값으로 고정하는 방식은 해당 자원을 확인하고 소유한 레거시 하드웨어 구성에 한정한다. `parport`가 관리하는 포트라면 `parport_register_dev_model()`로 클라이언트를 등록하고, 포트를 확보한 뒤 데이터·제어·IRQ 관련 연산을 사용하며 사용 종료 시 반납·등록 해제한다. 다른 드라이버가 관리하는 포트를 직접 제어하는 방식과 섞지 않는다. [병렬 포트 자원 관리](https://docs.kernel.org/driver-api/parport-lowlevel.html), [현재 parport 선언](https://github.com/torvalds/linux/blob/master/include/linux/parport.h)

GPIO 기반 보드에서는 해당 입력 GPIO의 디스크립터에서 `gpiod_to_irq()`로 IRQ를 얻는 등 플랫폼에 맞는 경로를 사용한다. 병렬 포트의 주소·핀·IRQ를 다른 보드에 그대로 적용할 수는 없지만, **이벤트를 기록하고 준비 조건을 갱신한 뒤 대기자를 깨운다**는 블로킹 I/O의 연결 방식은 유지된다. [GPIO와 IRQ 연결](https://docs.kernel.org/driver-api/gpio/consumer.html#gpios-mapped-to-irqs)
